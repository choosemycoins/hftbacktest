## 0. Контракт (не меняется, только расширяется)

1. **Указатели, а не ответы.** Каждый результат: `id` (`kb:<16 hex>`), вид, проект, дата, путь +
   чанк + диапазон строк / время / диапазон сообщений / sha, сниппет для ориентации.
   Открыть источник и прочитать — до того, как чему-то верить.
2. **БД — секрет.** В транскриптах лежат вставленные ключи и адреса. Файлы БД и матриц — 0600,
   каталог — 0700 (только если каталог наш: создан нами, пуст или несёт маркер `.kbindex-dir`;
   логика `_secure_dir` переносится как есть). Никогда не коммитится, не синкается, не копируется
   с машины. Производный артефакт: удалить и пересобрать.
3. **Всё, что выходит наружу, маскируется** (CLI, MCP, отчёты). Маскирование — сеть, не гарантия.
   Выход MCP попадает в контекст сессии Claude, то есть уходит провайдеру модели — поэтому
   маскируется каждая строка ответа и ответ ограничен по объёму (§9, §10).
4. **Пустой результат ≠ «не обсуждалось».** Покрытие и семантический охват выводятся в каждом
   ответе (§9).
5. **Сеть — только `kb fetch-model`** (разовая загрузка модели). Всё остальное работает и
   проверяется офлайн (§10.3).

## 3. Схема (SQLite, `PRAGMA user_version = 2`)

Схема v1 (одна FTS-таблица `kb`) не мигрируется: v2 открывает только `kb build --full` (§8.6),
который атомарно заменяет файл. Поиск по БД v1 — понятная ошибка «запусти `kb build --full`».

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);
-- schema=2, built_at, updated_at, update_seconds, emb_version (инкремент на каждую запись
-- эмбеддингов), active_model, parser_versions (json {kind: n}), config_sha

CREATE TABLE unit (                 -- единица изменения: файл, чат целиком, git-репо
  unit_id     INTEGER PRIMARY KEY,
  source_id   TEXT NOT NULL,        -- 'claude' | 'claude-memory' | 'repo:hftbacktest' | 'hft-research'
                                    -- | 'chat:deribit-ru' | 'course:cryptology10' | 'git:myhft' …
  rel         TEXT NOT NULL,        -- путь от корня источника; '' у чата и git
  kind        TEXT NOT NULL CHECK (kind IN
               ('transcript','export','memory','doc','note','chat','course','commit')),
  project     TEXT NOT NULL,
  abs_path    TEXT NOT NULL,        -- фактический путь на момент индексации (файл / каталог / корень репо)
  signature   TEXT NOT NULL,        -- json: [size, mtime_ns] | список таких по файлам экспорта | дайджест refs
  content_sha TEXT,                 -- sha256 байтов (однофайловые единицы)
  parser_ver  INTEGER NOT NULL,
  indexed_at  TEXT NOT NULL,
  title       TEXT NOT NULL DEFAULT '',
  UNIQUE (source_id, rel)
);

CREATE TABLE chunk (
  rowid      INTEGER PRIMARY KEY,   -- = rowid в chunk_fts
  chunk_id   TEXT NOT NULL UNIQUE,  -- 16 hex: sha256(source_id ␟ rel ␟ anchor)[:16]; повтор якоря в единице — первый свободный `#<n>` (§4.1 п. 6); коллизия между единицами — отказ этой единицы
  unit_id    INTEGER NOT NULL REFERENCES unit(unit_id),
  ordinal    INTEGER NOT NULL,      -- порядок внутри единицы (соседи для kb_read)
  anchor     TEXT NOT NULL,
  kind       TEXT NOT NULL,         -- денормализовано для фильтров
  project    TEXT NOT NULL,
  date       TEXT NOT NULL,         -- 'YYYY-MM-DDTHH:MM:SSZ'
  loc        TEXT NOT NULL,         -- 'L12-40' | 'L377' | 'message213023..213031' | 't=12:30-14:00' | '<sha>'
  file       TEXT,                  -- чат: 'messages52.html' / 'result.json'; иначе NULL
  title      TEXT NOT NULL DEFAULT '',  -- путь заголовков / чат·дата / сессия·роль / урок·время / тема коммита
  text       TEXT NOT NULL,         -- сырой, НЕмаскированный (поиск идёт по нему)
  stem       TEXT NOT NULL,         -- стемы(title + text) через пробел, в исходном порядке
  text_sha   TEXT NOT NULL,         -- sha256(title ␟ text) — ключ эмбеддинга
  n_chars    INTEGER NOT NULL
);
CREATE INDEX chunk_unit  ON chunk(unit_id, ordinal);
CREATE INDEX chunk_scope ON chunk(kind, project, date);
CREATE INDEX chunk_sha   ON chunk(text_sha);

CREATE VIRTUAL TABLE chunk_fts USING fts5(
  title, text, stem,
  content='chunk', content_rowid='rowid',
  tokenize='unicode61 remove_diacritics 2'
);
-- триггеры chunk_ai / chunk_ad / chunk_au — ровно по образцу «External Content Tables»
-- из документации FTS5 (delete со старыми значениями, затем insert).

CREATE TABLE emb_model (
  model_key   TEXT PRIMARY KEY,     -- 'e5b' | 'm3'
  repo_id     TEXT NOT NULL, revision TEXT NOT NULL,   -- ревизия = sha коммита HF, не 'main'
  dim         INTEGER NOT NULL, max_tokens INTEGER NOT NULL,
  query_prefix TEXT NOT NULL, passage_prefix TEXT NOT NULL,
  gen         INTEGER NOT NULL,     -- поколение файла матрицы emb/<model_key>/g<gen>.f16
  created_at  TEXT NOT NULL
);
CREATE TABLE emb_row (
  model_key TEXT NOT NULL REFERENCES emb_model(model_key),
  text_sha  TEXT NOT NULL,
  row       INTEGER NOT NULL,       -- номер строки в текущем поколении матрицы
  PRIMARY KEY (model_key, text_sha)
);
```

Удаление единицы — явно: `DELETE FROM chunk WHERE unit_id=?`, затем `DELETE FROM unit …`, в одной
транзакции. На каскад внешних ключей с триггерами FTS не полагаемся. Целостность проверяется
`INSERT INTO chunk_fts(chunk_fts) VALUES('integrity-check')` — в тестах и в `kb stats --check`.

Указатель для человека (`where`) собирается из `unit.abs_path` + `chunk.file` + `chunk.loc`:

| вид | `where` |
|---|---|
| doc / note / memory / export / курс-конспект | `/abs/path.md#L120-164` |
| transcript | `/abs/…/agent-x.jsonl#L377` (строка JSONL; `sed -n 377p`) |
| chat | `/…/ChatExport_2026-09-14 (1)/messages52.html#message213023` + `msg_range` |
| course ASR | `/…/transcripts/13.Риск-менеджмент.json#t=18:00-19:30` |
| commit | `/home/andrew/RustroverProjects/hftbacktest@9840d4a…` |

Часть разрезанного куска (> 1500 симв.) делит позицию с соседними частями (строка JSONL, sha,
докстринг, окно ASR/чата, одна длинная строка md), поэтому `loc` делается уникальным в пределах
единицы при записи (`store._chunk_rows`): k-я часть с уже встреченным `loc` получает `/p<k>` —
`…jsonl#L377/p2`, `…@<sha>/p2`, `…messages52.html#message213023/p2`. `where` называет ровно один
чанк, `kb read <where>` читает сам хит [ревью 07.10: в живом индексе 55 906 чанков в 8 370
группах с общим `loc`, 87 % — транскрипты].

## 4. Чанкинг

Общее: потолок **1500** символов (≈ 400–500 токенов XLM-R для русского; влезает в 512 у e5),
перекрытие **150** только при резке слишком длинной единицы; граница резки — абзац → строка →
пробел; ни один чанк не пустой. `text` хранится как в источнике; `title` — контекст (путь
заголовков и т.п.) и в FTS, и во входе эмбеддинга (`title + "\n" + text`), но не в `text`.

### 4.1 Markdown (doc, note, memory, курс-конспекты)
1. YAML-фронтматтер (`---…---` в начале) — часть первого чанка; `name`/`description` памяти —
   сжатое содержание, его нельзя терять.
2. Разделы по ATX-заголовкам `#`…`######` **вне** fenced-блоков (` ``` `, `~~~`).
3. Раздел < 300 символов сливается со следующим, пока сумма ≤ 1500; у слитого чанка `title` и
   `anchor` — первого раздела.
4. Раздел > 1500 режется по абзацам/строкам с перекрытием 150; таблица режется только по строкам.
5. `title` = `имя_файла › H1 › H2 › H3`; `loc` = `L<первая>-<последняя>` исходного файла (1-based).
6. `anchor` = путь заголовков + `#<n>` для повторов одинакового пути + `/p<k>` для частей.
   Переименование заголовка меняет id — это нормально (другой раздел). Якорь, всё равно
   совпавший с уже выданным в единице (заголовок, дословно равный сгенерированному: «X#2» после
   двух «X», «X/p2» после длинного «X»), получает первый свободный `#<n>` в порядке кусков
   (`store._chunk_rows`, для всех чанкеров): «X#2#2», «X/p2#2». Детерминированно — тот же файл
   даёт те же id; переименования считаются в `anchor_collisions` итога прогона [ревью 07.10:
   повтор якоря был ValueError, и одна такая заметка роняла весь update/build].

### 4.2 Простой текст (note `.txt`, `.rst`, докстринги)
Пакуются абзацы до 1500 с перекрытием; `anchor` = `p<k>`; докстринг — `docstring/p<k>`, `title` = имя
модуля. (`p<k>` нестабилен при правках выше — для этих видов приемлемо.)

### 4.3 Claude `/export` (export)
Ходы: строка `❯ ` — реплика оператора, `● ` (в старых версиях `⏺`) — блок ассистента;
продолжение — строки с отступом.
Выбрасываются: рамка баннера (строки из `╭│╰─▐▝▘` — в ней e-mail аккаунта), блоки `⎿` с
продолжением, строки `✻ …`, свёрнутые сводки инструментов (`Read N file…`, `ran N shell commands`).
Тем самым export подчиняется тому же правилу, что transcript: без ввода-вывода инструментов.
Чанк = ход (длинный режется); `anchor` = `t<n>/p<k>`; `loc` = строки файла.

### 4.4 Транскрипты (transcript)
Единица — строка JSONL с сообщением (`extract_message_text` без изменений). Сообщение ≤ 1500 — один
чанк; длиннее (в индексе v1 самое длинное — 263 631 симв. [замер 07.10]) — режется с
перекрытием.
`anchor` = `uuid` строки (есть у сообщений Claude Code) или `L<n>`, плюс `/p<k>`. `loc` = `L<номер
строки>`. `title` = `<сессия[:8]>/<файл агента> · <роль>`. Недописанная последняя строка
живой сессии — `malformed`, подхватится следующим прогоном.

### 4.5 Telegram (chat)
1. Разбор HTML `messages*.html` в порядке номера (регулярки из
   `~/hft-research/deribit-ru-chat-20260914/data/convert.py` — проверены на 328k сообщений:
   отправитель переносится на `joined`-сообщения, `<br>` → перевод строки, теги срезаются,
   `html.unescape`); или `result.json` (`text` бывает списком сущностей — склеить). Служебные
   и пустые — вон. Дата HTML: `title="12.07.2018 01:07:13 UTC+02:00"` → UTC; JSON: `date_unixtime`.
2. Экспорты одного чата сливаются по `id` сообщения; более новый экспорт выигрывает.
3. Окно: сообщения по `(date, id)`; новое окно при разрыве > 15 мин или если окно + сообщение >
   1500; сообщение > 1500 режется само. Строка окна: `HH:MM Отправитель: текст`.
4. `title` = `<название чата> · YYYY-MM-DD`; `anchor` = `m<id первого>/p<k>`; `loc` =
   `message<первый>..<последний>`; `file` = HTML-файл первого сообщения (якорь `#message<id>` в
   нём кликабелен в браузере).

### 4.6 Курс, ASR (course)
JSON `{file, model, device, duration, secs, segments:[{s,e,t}]}` ([замер 07.10]). Сетка 90 с:
окно k — сегменты с `s ∈ [90k, 90(k+1))`; `text` = их `t` через пробел; `anchor` = `t<90k>`
(устойчив к перерасшифровке другой моделью); `loc` = `t=mm:ss-mm:ss` (от `s` первого до `e`
последнего сегмента); `title` = `<курс> · <имя урока> · mm:ss`. Плотность речи ≈ 12 симв./с
[замер 07.10 по 5 файлам] → окно ≈ 1 080 симв., резка почти не нужна.

### 4.7 Коммиты
Один чанк (тема + тело), длинное тело режется; `anchor` = полный sha; `title` = тема;
`loc` = sha; `date` = дата автора.

## 5. Стемминг

- Токенизация как у FTS5 `unicode61`: `[^\W_]+` (подчёркивание — разделитель), NFKC, нижний регистр,
  **`ё → е`** (FTS5 `remove_diacritics 2` её **не** сворачивает: `еще` не находит `ещё` [замер 07.10]).
- Язык токена: есть кириллица → `snowballstemmer.stemmer('russian')`; латиница → `'english'`;
  цифры и смесь (`l2book`, `10006`) — как есть.
- `stem` = стемы `title + text` через пробел **в исходном порядке** (фразы и `NEAR` по стемам
  работают).
- Кэш `слово → стем` (dict на процесс): чистый Python даёт ~18k слов/с без кэша [замер 07.10 на
  копии snowballstemmer из poetry-venv] — на 22M слов корпуса это 20 мин; со словарным кэшем
  (Ципф) — минуты. PyStemmer (C) не ставим — заказ «pure Python».
- Качество [замер 07.10]: `комиссия/комиссии/комиссию → комисс`, `терял/терять/теряли → теря`,
  `ребейт*`, `ликвидац*`, `латентн*`, `requote*/requoting → requot`, `cancelled/cancels → cancel` —
  сходятся. Не сходятся: `отмена → отм` vs `отменить → отмен`, `троттл` vs `троттлинг`,
  `котирование/котировать/котировки`, приставки (`потерял`). Это закрывает семантика, а не
  подкрутка стеммера.
- Запрос (natural): токены → стемы → без стоп-слов (короткий встроенный список ru/en; если
  остались только стоп-слова — берутся все) → не больше 32 термов → `stem : ("s1" OR "s2" …)`,
  каждый терм в кавычках (`"` удваивается). Ранжирование — `bm25`.
- `raw:` в начале запроса — остаток уходит в FTS5 как есть по `{title text}` (прежняя семантика:
  точные формы, `*`, фразы, `NEAR`, `AND/OR/NOT`). Шим `kbindex.py search` всегда добавляет `raw:`.

## 6. Эмбеддинги

### 6.1 Интерфейс
```python
class Embedder(Protocol):
    model_key: str            # 'e5b' | 'm3' | 'fake'
    dim: int
    def embed_passages(self, texts: list[str]) -> np.ndarray: ...   # (n, dim) float32, L2-норма 1
    def embed_query(self, text: str) -> np.ndarray: ...             # (dim,)
```
- `FakeEmbedder(dim=64)` для тестов: стемы → blake2b → индекс и знак → сумма → нормировка;
  детерминирован, офлайн; необязательная тестовая таблица синонимов (`комиссия ~ fee`), чтобы
  тест показывал, что семантический список находит чанк без лексического пересечения.
- Реальный бэкенд: `sentence-transformers` на torch CPU (колесо с `download.pytorch.org/whl/cpu`).
  e5: префиксы `query: ` / `passage: `; bge-m3: без префиксов, CLS-пулинг из его `modules.json`.
  `max_seq_length = 512` у обоих (чанки ≤ 1500 симв.); батч 32, тексты сортируются по длине
  (меньше паддинга); `torch.set_num_threads(16)` в юните, 4 — в MCP; `show_progress_bar=False`.
- GPU (позже, сейчас GTX 1080 занята ASR): `--device cuda`. Карта Pascal (sm_61) — перед
  использованием проверить `torch.cuda.get_arch_list()`; новые CUDA-колёса Pascal могут не нести.

### 6.2 Модели и их загрузка
- `kb fetch-model --model e5b|m3` — **единственная сетевая команда**: `huggingface_hub.snapshot_download`
  в `HF_HOME=/home/storage/hft-scratch/hf-cache` с `allow_patterns` только для конфигов,
  токенайзера и `*.safetensors`; ревизия разрешается в sha коммита и пишется в
  `tools/kb/models.toml` вместе с sha256 и размером каждого файла.
- Если на ревизии нет safetensors (возможно у `BAAI/bge-m3` — проверить на загрузке), fetch
  явно докачивает только `pytorch_model.bin`, один раз конвертирует его через
  `torch.load(weights_only=True)` (torch ≥ 2.6) в safetensors, удаляет `.bin` и пишет хеши уже
  safetensors. Рантайм никогда не распаковывает pickle; `trust_remote_code=False`;
  `colbert_linear.pt`/`sparse_linear.pt` bge-m3 не качаются (dense only).
- Загрузка в рантайме: сверка размера и `mtime` с `models.toml` (дёшево); полная сверка sha256 —
  в ночном юните. Несовпадение → отказ семантики с явной причиной.

### 6.3 Выбор модели — правило записано до счёта
1. **Скорость.** `kb bench-embed --model X --n 2000` на фиксированной выборке реальных чанков
   (стратификация по видам пропорционально корпусу, seed `20261007`), CPU, 16 потоков, под
   `~/bin/hft-run -m 24G`: чанков/с, токенов/с, пиковый RSS → прогноз полного бэкфилла и
   суточной дельты.
2. **Качество.** Подкорпус: все чанки ожидаемых файлов golden (для каталогов чатов — окна, где
   встречается `must_contain`, не больше 200 на чат) + 10 000 случайных чанков-дистракторов
   (стратификация по видам, тот же seed). Обе модели — на одном подкорпусе; FTS ограничен тем же
   подкорпусом. Метрики — §13.
3. **Правило:** берём `m3`, если на гибриде (strict@10) он выигрывает **на ≥ 4 запроса больше,
   чем проигрывает** `e5b` (дискордантные пары), **и** суточная дельта на CPU ≤ 60 мин;
   иначе `e5b`. Бэкфилл в правило не входит: он разовый и дренируется по ночам или на GPU.
4. Решение и таблица чисел дописываются в §6.6 этого файла отдельным коммитом. Если гибрид с
   выбранной моделью не лучше стеммингового FTS хотя бы на 4 запроса — семантику всё равно
   включаем (заказ), но пишем это прямо.

### 6.4 Хранилище
- `<db_dir>/emb/<model_key>/g<gen>.f16` — сырой little-endian float16, построчно, без заголовка;
  число строк = размер / (2·dim). Каталог 0700, файл 0600.
- Адресация по содержимому: `emb_row(model_key, text_sha) → row`. Одинаковый текст в разных
  местах (повторы промптов, перенос раздела) эмбеддится один раз.
- Добавление: дописать строки в конец файла → `fsync` → вставить `emb_row` и `emb_version += 1` в
  одной транзакции. Номер строки считается от **фактического** размера файла, не от
  `max(row)+1`: оборванная дозапись оставляет хвост-мусор, но не ломает адресацию. Перед
  дозаписью файл усекается до кратного `2·dim` (недописанная строка после падения).
- Сборка мусора (`kb gc`, автоматически при мусоре > 25 % и > 10k строк): записать
  `g<gen+1>.f16` целиком → `fsync` → в одной транзакции переписать `emb_row` и `gen` → удалить
  старый файл. Падение до коммита — новый файл-сирота; после — старый файл-сирота; оба
  чистятся следующим прогоном. Читатель всегда открывает `g<gen>` из БД.
- Читатель (MCP, `kb search`): матрица — memmap float16 (e5 ~283 МБ, m3 ~377 МБ при 184k строк
  [оценка]); перезагрузка при смене `emb_version`. Скоринг: область < 20k чанков — сбор строк
  блоками по 32k и float32; область ≥ 20k — одно float16 matrix-vector в torch по всей матрице,
  затем точный float32-пересчёт лучших 1000 (ответ равен точному ранжированию, ничьи — по позиции).
  [замер 07.10, 193 689×1024, 4 потока: сбор+float32 в numpy 907–987 мс → двухступенчатый 58–89 мс].

### 6.5 Инкрементальный проход
`kb embed` (и `kb update --embed`): чанки, у чьего `text_sha` нет строки для активной модели →
порядок D14 → батчи → запись каждые 1000. Бюджет `--budget-minutes` / `--max-chunks`, по
исчерпании — чистый выход 0 и строка «осталось N». Смена модели = новое `model_key`, старая
матрица живёт до явного `kb gc --drop-model`.

## 7. Поиск и ранжирование

- **fts**: natural — по `stem` (§5), `raw:` — по `{title text}`. Фильтры `kind/project/since` —
  в SQL через `JOIN chunk`. Глубина 100.
- **semantic**: эмбеддинг запроса → косинус по чанкам в области фильтров (маски из метаданных,
  загруженных в память) → `argpartition` топ-100. Чанки без эмбеддинга не участвуют; ответ несёт
  `coverage = {embedded, in_scope}`.
- **hybrid**: `score = Σ 1/(60 + rank_l)` по двум спискам; равенство — по рангу fts, затем по дате.
  `raw:`-запрос в гибриде: fts — как raw, семантика — по тексту без операторов.
- Дедуп: одинаковый `text_sha` — остаётся самый ранний по дате.
- Разнообразие: не больше 3 чанков на ключ; ключ = `unit_id`, для чатов — `(unit_id, дата[:10])`
  (иначе фильтр `kind=chat` по одному чату давал бы 3 строки).
- Сниппет (на стороне Python, одинаково для всех режимов): окно в 40 токенов с максимумом
  совпадений стемов запроса (raw — сырых токенов, `*` — префикс), совпадения в `[ ]`, концы `…`,
  одна строка, ≤ 400 симв.; у чисто семантических хитов — первые 300 симв. `redact()` — ДО любой
  резки, по всему чанку: окно режется по границам токенов, а `:`/`-`/`_` делят токены, и окно,
  начатое внутри секрета (токен бота `<id>:<35>`), показывало бы хвост, который правила не узнают.
- `raw:`: `*` — только сразу после слова и без цифр в нём (`теря*`, не `0x7a*`, не `"…"*`, не
  `слово *`): «нашлось / не нашлось» по маскированному тексту выписывает ключ по символу [ревью
  07.10: случайный 0x-ключ восстанавливался целиком за ≤ 1024 запроса через MCP]. Не закрыто:
  значение из одних букв (`password=…`) выписывается буквенными префиксами.
- Ответ: `limit` по умолчанию 10, максимум 50; запрос ≤ 2000 симв.
- Цели скорости [проверяются на приёмке]: fts p50 < 300 мс, hybrid p50 < 1.5 с на тёплом
  процессе (без первой загрузки модели).

## 8. Инкрементальная пересборка

### 8.1 Алгоритм `kb update`
1. Писательская блокировка `flock(<db_dir>/kb.lock)`; занято → таймер выходит 0 со строкой
   «другой писатель», ручной запуск ждёт до `--lock-timeout`.
2. Гарды до первой записи: свободно на ФС БД ≥ 5 ГБ (`--min-free-gb`); PSI памяти
   `user@1000.service` `some avg10 ≤ 20` — иначе ждать до `--psi-wait-minutes 60`, затем exit 75.
3. По каждому источнику — перечисление кандидатов (правила §2.1) → `{rel: (size, mtime_ns)}`.
4. По единице: нет в БД → разобрать, вставить. Подпись та же и `parser_ver` тот же → пропуск.
   Подпись другая → `sha256` байтов; совпал → обновить подпись, пропуск (touch); иначе
   разобрать и сделать diff по `chunk_id`: тот же id и `text_sha` — не трогать; тот же id, другой
   `text_sha` — update (триггеры переиндексируют FTS); новые — insert; исчезнувшие — delete.
   Одна единица = одна транзакция. Единица, которая не разобралась или не записалась (значение,
   которое не берёт ни один UTF-8-кодировщик, — экранированный одиночный суррогат в JSONL;
   ограничение), — `warn` с путём и типом ошибки, `failed += 1`, exit 3; её транзакция
   откатывается, старая версия в индексе остаётся, следующий прогон пробует снова; остальные
   единицы индексируются. Отказ самой БД (`OperationalError`: занята, нет места, I/O, только
   чтение; голый `DatabaseError`: битая) останавливает прогон, как раньше: на нём упала бы каждая
   следующая единица.
5. Чат: подпись = отсортированный список `(файл, size, mtime_ns)` по всем экспортам из allowlist;
   изменилась → перечитать все экспорты чата, слить, diff.
6. Git: подпись = sha256 вывода `git for-each-ref` + `HEAD`; изменилась → `git log --all`, diff по sha.
7. Удаления (§8.2) → `meta.updated_at` → при `--embed` проход §6.5 → FTS `merge` (после крупных
   изменений — `optimize`).
8. Итог в stdout (журнал юнита): по видам — добавлено/изменено/удалено/пропущено/битых строк,
   секунды; **никогда не текст чанков**.

### 8.2 Удаления и защиты
- Файл исчез при **существующем и непустом** корне → единица удаляется.
- Корень отсутствует/нечитаем → удалений по этому источнику нет, предупреждение, итоговый exit 3
  (как сейчас). Это случай «не смонтирован `/home/storage`».
- Массовое удаление: если источник потерял бы > max(50 единиц, 20 % своих) за прогон — удаления по
  нему не выполняются, exit 3, нужен `--allow-mass-delete`.
- Источник или чат убран **из конфига** — его единицы удаляются без гарда (намеренное действие),
  с записью в журнал.
- `parser_ver` вида вырос → все единицы вида перечитываются; id стабильны по якорю, а
  эмбеддинги переиспользуются по `text_sha` — повторного счёта модели нет.

hftbacktest в зеркале 14, живьём 8; по всем слагам только в зеркале лежат 7 JSONL (0.1 МБ)

### 8.4 Правило удержания
Для `source_id='claude'` кандидаты = объединение по относительному пути: живой
`~/.claude/projects` **выигрывает**, зеркало (`retain_from` в конфиге) добавляет только то, чего нет
живьём. `rel` одинаков, значит `chunk_id` не меняется при переезде live → зеркало. Только для
транскриптов; память и всё остальное — только живые.

### 8.5 Блокировки и читатели
Журнал rollback (`journal_mode=DELETE`), `busy_timeout = 5000` у всех соединений. Читатели
открывают `mode=ro`; сменился `st_ino` файла БД — переоткрыть (поколение соединения +1).
Семантические массивы (rowid → строка матрицы, маски kind/project/date) перегружаются по штампу
(поколение соединения, `PRAGMA data_version`): `data_version` двигается на **любой** коммит
другого соединения — `kb update` без `--embed`, шим, дозапись векторов, gc. Один поиск — одна
читающая транзакция (`store.snapshot`): meta, массивы, fts, выборка строк и `coverage` видят одно
состояние; вектор запроса считается до неё (ожидание модели не держит блокировку). Под открытым
снимком соединение не подменяется. [Ревью 07.10: штамп по `emb_version` пропускал правки `kb update`
— KeyError в hybrid, ранжирование по вектору старого текста.]

Ошибки состояния БД объясняются, а не сводятся к «пересобери» (`store.explain`): busy/locked —
повторить; горячий журнал прерванной записи (SIGKILL, питание), который `mode=ro` откатить не
может, — `kb update` (откатывает, векторы на месте); только не-БД / чужая схема — `kb build --full`.

### 8.6 Полная пересборка `kb build --full`
Во временный файл рядом → перенос `emb_model`/`emb_row` из живой БД (матрицы те же, адресация по
`text_sha`, модель не пересчитывается) → `fsync` → `os.replace`. Временный файл и его
`-journal` чистятся при любой ошибке (как сейчас). WAL не используется именно здесь: живой
читатель держал бы `kb.db-wal` старого файла, а новое соединение к новому `kb.db` подхватило бы
чужой WAL. Отдельно `kb update` после `--full` не нужен.
Первым делом под локом живая БД открывается на запись (`store.recover`): её первое чтение
откатывает горячий журнал. Иначе ro-чтение старого файла падало, перенос векторов молча давал 0,
а журнал старого файла переживал `os.replace` и проигрывался в новый (malformed) [ревью 07.10].
Ошибка чтения векторов v2-БД (busy, нечитаемая таблица) — отказ сборки (`kb build` → 3), старый
файл не тронут; «не SQLite вовсе» — предупреждение и сборка без векторов.

## 9. MCP-сервер

- `kb mcp` — FastMCP из пакета `mcp`, **только stdio** (`mcp.run()` без аргументов транспорта;
  тест проверяет, что сетевых транспортов в модуле нет). БД — `mode=ro`. Модель грузится в фоне
  сразу после старта; первый семантический запрос ждёт её до 60 с, дальше — деградация в fts с
  полем `degraded`.
- **stdout — канал протокола.** Любой `print`, прогресс-бар `tqdm`/`transformers` или
  предупреждение в stdout ломает JSON-RPC. Логи — только stderr; `HF_HUB_DISABLE_PROGRESS_BARS=1`,
  `TQDM_DISABLE=1`, `TRANSFORMERS_VERBOSITY=error`. Тест: в stdout сервера только кадры протокола.
- Самопроверка при старте: в `/proc/net/dev` только `lo` (иначе отказ стартовать с текстом, как
  запускать правильно), `HF_HUB_OFFLINE=1` и `TRANSFORMERS_OFFLINE=1` выставляются кодом
  принудительно до импорта `transformers`.

**`kb_search(query, mode="hybrid", kind=None, project=None, since=None, limit=10)`**
- `mode`: `hybrid | fts | semantic`; `kind`: вид или список через запятую; `since`: ISO-дата;
  `limit` ≤ 50.
- Ответ:
```json
{"notice": "kb: pointers, verify at source … masked best-effort … keep local",
 "index": {"updated_at": "…", "age_hours": 6.2, "model": "e5b"},
 "query": {"mode": "hybrid", "used": "hybrid", "raw": false, "terms": ["комисс", "lighter"]},
 "coverage": {"embedded": 151230, "in_scope": 183977},
 "degraded": null,
 "results": [{"id": "kb:9f1c2a7d3e4b5a60", "kind": "note", "project": "lighter-latency-race-20260921",
   "date": "2026-09-21T15:20:00Z", "title": "RESULT.md › 2. Вердикты",
   "where": "/home/andrew/hft-research/lighter-latency-race-20260921/RESULT.md#L40-71",
   "snippet": "… тейкер [−1.86] бп …", "score": 0.0325, "ranks": {"fts": 3, "sem": 1}}]}
```
- `query.terms` — стемы (у `raw:` — слова и `префикс*`). Термин — кусок запроса в нижнем
  регистре (`:`, `-`, `_` режут токены), и по кускам ни одно правило маски ключ не узнаёт;
  поэтому показывается только термин, который даёт и запрос, маскированный тем же `redact()`,
  остальные — `[redacted]` (`search.shown_terms`, общий путь CLI `--json` и MCP) [ревью 07.10:
  ключ Binance, вставленный в запрос, возвращался в `terms` целиком, токен бота — четырьмя
  кусками].

**`kb_read(pointer, context=1)`**
- `pointer`: `kb:<id>` или ранее выданный `where` (в том числе с `/p<k>`, §3); резолвится **только** через БД. Путь, которого
  нет в индексе, — ошибка; файлы с диска не читаются (кроме `os.stat` проиндексированного пути
  для флага `stale`).
- `context` 0…5 соседних чанков той же единицы с каждой стороны (у коммитов — 0).
- Ответ: `{id, where, kind, title, stale, text, before: [...], after: [...]}`; все строки через
  `redact()`; суммарно ≤ 20 000 симв. (соседи урезаются первыми).

**Регистрация (выполняет лид, здесь не выполнять):**
```bash
claude mcp add kb -s user \
  -e HF_HOME=/home/storage/hft-scratch/hf-cache -e HF_HUB_OFFLINE=1 -e TRANSFORMERS_OFFLINE=1 \
  -- /usr/bin/unshare -rn /home/storage/hft-scratch/kb-venv/bin/kb mcp
```
`unshare -rn` (user + net namespace) отрезает сеть целиком: внутри только `lo`, чтение файлов
пользователя работает [замер 07.10]. `unshare` без `--fork` делает `exec` — сигналы Claude Code
доходят до сервера напрямую. Память: модель + матрица ≈ 1.5–3 ГБ на каждую сессию Claude,
поднявшую сервер.

## 10. Безопасность

### 10.1 Хранилища
| что | где | режим |
|---|---|---|
| БД, `-journal`, `kb.lock` | `~/.local/share/kbindex/` | файлы 0600, каталог 0700 (маркер `.kbindex-dir`) |
| матрицы | `<db_dir>/emb/<model>/` | 0700 / 0600 |
| отчёты eval, бенчи | `<db_dir>/eval/` | 0700 / 0600; только указатели и метрики, без текста |
| конфиг с allowlist чатов | `~/.config/kb/kb.toml` | 0600, каталог 0700, не в git |
| модели | `/home/storage/hft-scratch/hf-cache` | публичные веса; целостность — sha256 из `models.toml` |
| venv, uv-кэш | `/home/storage/hft-scratch/{kb-venv,uv-cache}` | секретов нет |

- Процесс ставит `os.umask(0o077)` первой строкой CLI → всё, что создано (включая журнал SQLite,
  временные файлы, матрицы), рождается 0600/0700. Юнит дублирует `UMask=0077`.
- Вектора эмбеддингов частично обратимы в текст — матрица секретна наравне с БД.
- Журналы (journald читает группа `adm`): только счётчики, пути и id, без текста и сниппетов.
- `/home/storage` — 0777, и на машине есть второй локальный пользователь (не в группе `andrew`)
  [замер 07.10]: поэтому ни БД, ни матрицы не кладём в `hft-scratch` (0775) по умолчанию.

### 10.2 Маскирование (`redact`, расширяется по TDD)
Сохраняется всё нынешнее (0x-значения, hex ≥ 48, JWT, bearer/basic, `sk-/pk-/rk-`, GitHub, Slack,
AWS, `key=value` для имён-секретов). Добавляется, каждое со своим тестом и тестом на ложное
срабатывание:
- PEM-блок `-----BEGIN … PRIVATE KEY----- … -----END … PRIVATE KEY-----` → `[redacted:pem]`;
- токен Telegram-бота `\b\d{8,10}:[A-Za-z0-9_-]{35}\b` → `[redacted:tg]`;
- base58 ≥ 80 (`[1-9A-HJ-NP-Za-km-z]`) — приватные ключи Solana → `[redacted:b58]`;
- `xai-[A-Za-z0-9]{20,}`, `hf_[A-Za-z0-9]{30,}`, `AIza[0-9A-Za-z_-]{35}` → `[redacted:token]`;
- смешанный высокоэнтропийный токен: ≥ 32 символов `[A-Za-z0-9+/]`, есть строчные, заглавные и
  цифры → `[redacted:entropy]` (ключи API Binance — 64 таких символа). Не задевать: git-sha (40
  hex, нижний регистр), uuid с дефисами, `snake_case`-идентификаторы;
- `NAME=…`, `NAME: …`, `NAME = …`, `"name": "…"`, где имя **содержит** слово (регистр любой):
  password, passwd, passphrase, secret, token (не `tokeniz…`), api_key, private_key, mnemonic,
  seed_phrase, credential — `DB_PASSWORD`, `BYBIT_API_KEY`, `apiSecret`, `x-api-key`: значение →
  `[redacted]`, имя и разделитель остаются. Значение любой длины; в кавычках — до закрывающей
  (незакрытая — до конца строки); только та же строка; разделитель — пробелы, табы, NBSP; `==` —
  сравнение, не присваивание; имя ≤ 64 символов вокруг слова (иначе квадратичное время на длинном
  прогоне). [Ревью 07.10: `\bpassword\b` пропускал склеенные имена, значение < 6 символов и
  кавычки с пробелами (мнемоника) выходили открытыми. Замер 07.10 на живом индексе, 195 176
  чанков: старое правило — 130 чанков, новое — 430, только старым — 0 (первая версия теряла
  чат с NBSP — разделитель расширен). Ложные срабатывания в основном у token (`max_tokens=4096`,
  `tokens = text.split()`) — приняты: сниппет — ориентир, источник читается всё равно];
- пароль в URL `scheme://user:password@host` → `scheme://user:[redacted]@host` (пароль — до
  последнего `@` перед хостом; порт и `user@host` без пароля не трогаются; 11 чанков живого
  индекса).
Маскирование применяется ко **всем** строкам ответа MCP и CLI (`snippet`, `text`, `title`, соседи),
к stderr CLI и к трейсбеку необработанного исключения (`sys.excepthook`: хвост журнала ночного
юнита уходит в Telegram через `OnFailure`, §11.4).

### 10.3 Сеть
- В коде: `os.environ['HF_HUB_OFFLINE']='1'`, `TRANSFORMERS_OFFLINE=1`, `HF_DATASETS_OFFLINE=1`,
  `HF_HUB_DISABLE_TELEMETRY=1` — **принудительно** (не `setdefault`) во всех командах, кроме
  `fetch-model`, до импорта `huggingface_hub`/`transformers`.
- Структурно: MCP — под `unshare -rn`; юнит — `PrivateUsers=yes` **и** `PrivateNetwork=yes`.
  Ловушка [замер 07.10, systemd 249]: в user-юните один `PrivateNetwork=yes` **молча не работает**
  («network namespace setup failed, ignoring: Operation not permitted» — сеть остаётся); с
  `PrivateUsers=yes` — только `lo`.
- Самопроверка `--require-offline` (по умолчанию у `update`, `embed`, `mcp`): множество
  интерфейсов в `/proc/net/dev` (он per-netns) == `{lo}`, иначе отказ. Без попыток соединения —
  проверка сама не ходит в сеть.

### 10.4 Чего индекс не читает
Файлы по маске секретов (§2.1); `~/.config/**`, `~/.ssh/**` не входят ни в один корень; личные
чаты — только через явный allowlist; tool_result/tool_use транскриптов и блоки `⎿` экспортов —
не индексируются (там чаще всего лежат ключи и выводы `cat`).

## 13. Eval

`tools/kb/eval/golden.jsonl` — 81 запрос (46 ru, 35 en), выведены из `MEMORY.md` и файлов памяти,
`RESULT.md` исследований, дизайн-нот и `AGENTS.md`; каждый проверен при записи: ожидаемые пути
существуют, хотя бы один `must_contain` встречается хотя бы в одном из них [проверено 07.10].

Поля: `id`, `query`, `lang`, `tags`, `expect` (любой из), `must_contain` (любой из), `filters`
(необяз.), `note`. Теги: `venue` 30, `number` 26, `xling` 31 (язык запроса ≠ язык основного
источника), `paraphrase` 22, `verdict` 22, `design` 20, `exact` 17, `chat` 13, `ops` 5, `course` 4,
`filter` 2, `kind:{doc,note,commit,transcript,export}` — по одному-два.

Правила совпадения:
- путь с `/` на конце — префикс каталога (экспорты чатов); `repo@sha` — коммит с этим префиксом
  sha; иначе точный путь (после `expanduser`);
- **hit@k** — в первых k есть чанк ожидаемого пути; **strict@k** — и его текст (без учёта регистра
  и пробелов) содержит один из `must_contain`; **MRR@10** — по первому hit.

Режимы: `fts_raw_or` (несемантический базис: те же термы через OR по сырому `text`, без стемминга —
мера вклада стемминга), `fts`, `semantic`, `hybrid`. Отчёт — по всем запросам и по тегам,
плюс дискордантные пары для сравнения моделей (§6.3). Перед счётом — дрейф-чек: запрос, чей файл
пропал или потерял литерал, уходит в список `drifted` и не считается промахом.
Приёмка стемминга: `fts` не хуже `fts_raw_or` по strict@10 (не меньше запросов с hit).

⚠️ Репозиторий-форк публичный. `golden.jsonl` и этот файл не содержат секретов, адресов
аккаунтов и имён частных лиц, но содержат темы исследований и локальные пути — перед любым
пушем ветки решение за оператором (§15.2).
