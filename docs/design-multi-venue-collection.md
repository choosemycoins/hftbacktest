# Design: сбор маркетдаты с нескольких бирж

Статус: Draft, ревизия 2 — предложен, не утверждён
Дата: 2026-07-26
Область: `collector/` — многобиржевая запись и сборка датасета для мультиассетного бэктеста
Связано: [`design-hyperliquid-connector.md`](design-hyperliquid-connector.md),
`AGENTS.md` §4 (ловушки кодовой базы), §2 (красная линия про оптимизацию до измерений)

> Ревизия 2. Первая версия прошла три проверяющих агента и была переписана по существу:
> эксперимент из Фазы 1 мерил величину со знаком наоборот, фикс бага 0.1 не чинил тот отказ,
> ради которого писался, а защита 0.4 имела гонку, срабатывающую при каждой перезагрузке.
> Разбор каждого — по месту. Ничего из перечисленного ниже ещё не реализовано.

## Контекст

Нужны стаканы с нескольких площадок с сопоставимыми таймстемпами, для мультиассетного
`hftbacktest`.

**Часы на одном хосте сопоставимы, и это не требует работы.** Все пять бэкендов штампуют
`Utc::now()` первым оператором в ветке `Message::Text`, до парсинга
(`binance/http.rs:82`, `binancefuturesum/http.rs:83`, `binancefuturescm/http.rs:83`,
`bybit/http.rs:74`, `hyperliquid/http.rs:67`). Процессы на одном хосте читают один
`CLOCK_REALTIME`.

Важное уточнение, которого не было в первой версии: сопоставимость **между инстансами одного
хоста** требует **общих** часов, а не **правильных**. Хост, ушедший на пять секунд, всё равно
даёт сопоставимые межинстансные метки. Абсолютная правильность нужна только при сравнении с
биржевым `E`/`T`. Из этого следует, что мониторинг дисциплины часов в план не входит, а
`Utc::now() − Instant::now()` его бы и не дал: на Linux `CLOCK_MONOTONIC` слюится вместе с
`CLOCK_REALTIME`, так что слюинг такой детектор не видит. Нужен был бы `ntp_adjtime` или
`chronyc tracking`.

**Чего реально не хватает.** Три вещи, и все три — в нашем коде:

1. **Коллектор может часами быть `active` и не писать ничего.** Любой отказ, кроме голого
   TCP FIN — геоблок, отказ DNS, отклонённая подписка, полуоткрытый сокет, — уводит
   `keep_connection` в ветку `Err`, и она переподключается **вечно**. Выход 0, юнит здоровый,
   данных нет.
2. **Два коллектора в одной директории уничтожают данные друг друга.** `Writer` ключует файлы
   по `symbol.to_lowercase()` без компоненты биржи (`file.rs:362,370`), `BTCUSDT` есть на трёх
   биржах, и два `GzEncoder`, дописывающих 48-килобайтными блоками в один файл, делают его
   **недекодируемым**. Комментарии в `file.rs:336-341` и `collector/README.md:149-151`
   утверждают обратное — оба ложны.
3. **Сборки кросс-биржевого датасета нет.** Проверено: ни одного примера с одним `Backtest`
   над активами двух бирж во всём репозитории.

## Фаза 0 — сделать коллектор пригодным к многобиржевой работе

Проверять: `cargo test --workspace --lib --bins` (**не** `--all-targets`, четыре примера не
компилируются), `cargo clippy -p collector --bins` без новых предупреждений сверх измеренных
семи, `cargo +nightly fmt`.

**0.1 `feat(collector): fail when no market data arrives`** — главный.
Сторожевой таймер на данные: если за N минут не записано ни одной **не-`_meta`** записи,
`fatal` и ненулевой выход. Около десяти строк рядом с `disk_check` в существующем `select!`
(`main.rs:335`). Порог в конфиг, дефолт минут пять — заметно больше самого редкого фида
(`l2Book slow` у HL раз в 5.4 с).
Это чинит отказ **целиком**, для всех причин. Всё остальное ниже — гигиена вокруг него.

**0.2 `fix(collector): let the collection channel close`**
Убрать `.clone()` и передать `ws_tx` по значению: `binance/mod.rs:85`,
`binancefuturesum/mod.rs:86`, `binancefuturescm/mod.rs:86`, `bybit/mod.rs:43`,
`hyperliquid/mod.rs:341`. Проверено — ни в одном из пяти `ws_tx` больше не используется, REST-
задачи Binance клонируют `writer_tx`, а не `ws_tx`, конфликта нет.
**Честно о границах:** это закрывает только чистый EOF. Тест «канал закрылся ⇒ ненулевой
выход» писать не надо — `main.rs:368-389` эту половину обрабатывает правильно уже сегодня,
такой тест зелёный и до фикса. Регрессия здесь ловится сторожевым таймером из 0.1.

**0.3 `fix(collector): make the reconnect backoff ladder reachable`**
`if error_count > 3 {1s} else if > 10 {5s} else if > 20 {10s}` — вторая и третья ветки
недостижимы. `binance/http.rs:161`, `binancefuturescm/http.rs:162`,
`binancefuturesum/http.rs:162`, `bybit/http.rs:137`. У `hyperliquid/http.rs:175-181` порядок
правильный — там это уже чинили и не перенесли. Плюс `.timeout()` на REST-клиент
(`binancefuturesum/http.rs:45-55`), сейчас его нет и зависшее чтение держит клон `writer_tx`.
Без этого геоблокированный Binance будет молотить TLS-хендшейки раз в секунду.

**0.4 `fix(collector): lock the output directory`**
Не сканирование имён, а `flock(LOCK_EX|LOCK_NB)` на `<dir>/.collector.lock` на всё время
жизни процесса, с записью имени инстанса и pid внутрь. Сканирование имело пять дыр, из них
две смертельные: гонка при параллельном старте (systemd поднимает инстансы одновременно при
загрузке, `install.sh:225-243` перезапускает их пачкой при каждом деплое), и «мета-файл увезли,
символьные остались» — тогда проверка проходит и файл дня становится недекодируемым.
`flock` атомарен, переживает ротацию sidecar, не зависит от даты, и даёт имя и pid живого
держателя, чего скан дать не может.
Плюс одна строка в `collector-run.sh:23`: `${COLLECTOR_DATA_DIR:-/opt/hft-collector/data/${INSTANCE}}`,
`COLLECTOR_INSTANCE=%i` юнит уже выставляет (`hft-collector@.service:51`). Это делает коллизию
структурно недостижимой, а замок оставляет как страховку.
Переписать оба ложных комментария — `file.rs:336-341` **и** `collector/README.md:149-151`.

**0.5 `feat(collector): pass the instance name to the binary`**
`collector-run.sh` сегодня использует `COLLECTOR_INSTANCE` только как префикс лога, в `exec`
(строка 80) он не попадает. Добавить `--instance` с дефолтом из биржи. Нужно **до** любого
запуска двух инстансов одной биржи: сейчас sidecar называется по бирже (`main.rs:315`), так
что у двух таких инстансов теги совпадут.

## Фаза 1 — измерить джиттер по данным, которые уже лежат на диске

**Эксперимент с двумя инстансами из первой версии выброшен.** Он мерил не ту величину, причём
с оптимистичным смещением. Два инстанса на одном хосте, читающие одну биржу, делят маршрут,
интерфейс, конгестию — ковариация сетевого члена большая и положительная, и в попарной разнице
он **сокращается**. А межбиржевая величина, ради которой всё затевалось, идёт по двум разным
маршрутам с независимой конгестией, там ковариация около нуля и дисперсия пути выживает
целиком. То есть A/B давал бы **нижнюю** границу, а я назвал её верхней. По той же причине
`σ ≈ stdev(Δ)/√2` неверно: тождество требует нулевой ковариации.

**Что мерить вместо этого:** `local_ts − E·1e6` по каждой бирже, один инстанс, на **уже
записанных** `.gz`. Разброс этой величины (p99 − p50) и есть весь бюджет ошибки для этой
биржи — постоянное смещение часов биржи в разность попадает константой и из разброса выпадает.
Ноль деплоя, ноль новых инстансов, считается сегодня по тому, что записано.

Оговорка честно: `E` квантован до миллисекунд (одно это даёт σ≈0.29 мс), поэтому полосу
«меньше миллисекунды» такой метод не разрешает. Но он разрешает «1–10 мс» и «больше 10 мс», а
только эти две полосы меняют решения.

Считать по каждой бирже: p50, p90, p99, p99.9 от `local_ts − E`; **разброс** p99−p50 как
рабочее число; то же в разбивке по каналам (у HL `bbo` против `l2Book`, у Binance `trade`
против `depth`) — межканальная разница и есть систематический сдвиг от стоимости
декодирования, которого A/B не видел бы в принципе.

**Правило решения** — по **разбросу p99−p50**, единая шкала, без пересечений:

| Разброс | Что делать |
|---|---|
| **< 10 мс** | Достаточно для сигнальной второй биржи и для базисных стратегий. Записать число в `collector/README.md`, горячий путь не трогать. |
| **10–50 мс** | Сделать 2.2 (дешёвая часть), перемерить по тем же файлам. |
| **> 50 мс** | Запись — ограничивающий фактор. 2.2 целиком до сборки любого датасета. |

Если после этого понадобится разрешать доли миллисекунды — тогда и только тогда A/B, но с
исправлениями: склейка по интервалу `(U, u)`, а не по `u` (Binance коалесцирует дельты
по-разному на разных edge-серверах, и осиротевшие сообщения коррелируют с нагрузкой, то есть
обрезают именно хвост); первичный ключ на `@trade`/`t`, трейды не коалесцируются; прогон
через UTC-полночь, потому что ротация файлов всех символов разом — крупнейший стопор в
системе и в часовой прогон не попадает; и обязательная запись `CPUCreditBalance` и `%steal` —
t4g.small burstable, часовой прогон внутри кредитов и неделя на базовой линии дадут разные
числа.

**Топология: один хост.** На одном хосте смещение общее и сокращается. Хосты по регионам
покупают меньшую задержку до каждой биржи, а это ровно то, что моделирует
`FeedLatencyAdjustment` (`backtest/mod.rs:186-194`, пример Binance-Токио / Bybit-Сингапур в
`data/reader.rs:449-464`). Менять сокращающееся смещение на моделируемую разницу — плохая
сделка.

**Несколько процессов, а не один** — и решающий довод не в изоляции отказов. `writer.write` →
`GzEncoder::write_all` это **синхронный не-yield-ящий** вызов внутри tokio-задачи. В одном
процессе на двух воркерах всплеск у одной биржи блокирует воркер на всё время сжатия, и
планировщик tokio его не вытеснит — очередь из десяти 48-килобайтных блоков это 10–30 мс
head-of-line для читающих задач **всех** бирж. В отдельных процессах вытесняет ядро, и
прогресс гарантирован квантом CFS. Плюс один процесс на две биржи немедленно упирается в
коллизию имён файлов из пункта 2 контекста.

## Фаза 2 — многобиржевая запись

**Раскладка: одна директория на инстанс, биржу в имя символьного файла не вносить.**
Переименование раскладки — дверь в одну сторону, обесценивающая все существующие записи и
команды, и не дающая ничего сверх директории. Добавление биржи остаётся «добавить один
env-файл»: `install.sh:228` перебирает `etc/*.env` глобом, `ReadWritePaths` покрывает
подкаталоги.

**2.1 `docs(collector): document recording several venues on one host`**
Один инстанс на биржу, одна директория на инстанс (теперь под замком); таймстемпы из одного
`CLOCK_REALTIME` и потому сопоставимы между инстансами — это и есть свойство, на которое
опирается мультиассетный бэктест; число разброса из Фазы 1 с условиями получения.
**Бюджет диска пересчитать.** Цифры в `README.md:493-508` — HL 22 МБ/сутки на символ, Bybit
86–159 — не покрывают Binance USD-M с `@trade` + `@bookTicker` + `@depth@0ms`, это другой
порядок, правдоподобно единицы гигабайт в сутки на инстанс. И существенное: `check_disk` при
пробитии порога — **фатальный выход у каждого инстанса на этой файловой системе**, а не только
у прожорливого.

**2.2 (по итогам Фазы 1) горячий путь**, в правильном порядке:

1. **`Compression::new(1)` вместо `Compression::default()`** в `file.rs:93`. Уровень 1 дешевле
   по CPU в 3–5 раз ценой 10–15% объёма, а объём при 22 МБ/сутки — шум. Одна строка, лучшее
   отношение эффекта к правке во всём плане, и в первой версии его не было.
2. Убрать `statvfs` из `check_disk` (`main.rs:335`) в `spawn_blocking`.
3. Только вместе с (4): зафиксировать `worker_threads` (`main.rs:158`).
4. Вынести gzip в выделенный поток ОС, владеющий `Writer`. **Порядок важен:** поставить
   `worker_threads = 1` раньше, чем убран inline-gzip, — регрессия, сжатие заблокирует
   собственные читающие задачи процесса. Обоснование не «`Writer` не `Sync`» (это, скорее
   всего, неверно, да и `spawn_blocking` требует `Send`), а насыщение пула. И это перенос
   работы, а не её устранение: на двух ядрах контеншен тот же. Делать последним и только если
   (1) не хватило.

Отдельно, вне очереди: `writer_tx` — `unbounded_channel`, зависший писатель растёт без границы
на двухгигабайтном хосте.

## Фаза 3 — данные для первого прогона

Строить почти нечего: торгуемая биржа конвертируется существующим конвертером.

**3.1 Сдвиг `correct_local_timestamp` брать из вывода конвертера, а не пересчитывать.**
`validation.py:46` уже печатает `'local_timestamp is ahead of exch_timestamp by', -latency`.
Проверка `min(local_ts − exch_ts)` по `.npz`, которую я предлагал, **тавтологична**: после
сдвига минимум равен ровно `base_latency` по построению. Магнитуду можно получить только по
сырому `.gz`. И сдвиг применяется **на файл, то есть на сутки**, поэтому у тридцатидневного
набора может быть тридцать разных констант — фиксировать надо при каждой конвертации, а не
один раз руками.

**3.2 Файл задержки ордеров для торгуемого актива.** `BacktestAsset::new()` по умолчанию даёт
`ConstantLatency { entry: 0, resp: 0 }` — **нулевую задержку, молча**
(`py-hftbacktest/src/lib.rs:134-140`). Все рабочие примеры вызывают `.intp_order_latency(...)`.
`generate_order_latency` уже есть (`feed_order_latency.py`), но вызвать его надо явно, иначе
получится тот самый молча-оптимистичный бэктест.

**3.3 Начальный снапшот и защита от пустого стакана в первый день.**
`create_last_snapshot` (`snapshot.py:9-55`) строит день N из дня N−1 — значит **у первого дня
свежей записи предшественника нет и снапшота не будет**. Стакан стартует пустым: `best_bid()`
даёт `NaN`, `best_bid_tick()` даёт `INVALID_MIN` (`depth/mod.rs:21,38`), сравнения с NaN молча
ложны. При этом массив-сигнал покрывает все сутки и читается валидно — то есть стратегию будят
с живым сигналом и мёртвым стаканом. Это происходит **в рекомендованной конфигурации, в первый
же день тех данных, что пишутся прямо сейчас**. Проверка `best_bid_tick() != INVALID_MIN`
нужна с одним активом, а не только с двумя.

**3.4 Массив-сигнал.** `(N, 2)` из `.gz` второй биржи: `local_ts` и нужная величина. Идиома —
`examples/Integrating Custom Data.ipynb`, около двадцати строк. Смещать на тот же сдвиг, что
конвертер применил к торгуемому активу (3.1), иначе сигнал сдвинут ровно на него и никто не
пожалуется. Любой ресемпл — только назад, иначе заглядывание в будущее.

## Фаза 4 — что дальше

**Слово «безусловно» из первой версии убрано.** Оно противоречило собственному открытому
вопросу, и подсчёт стоимости был завышен.

Честная стоимость второго **торгуемого** актива против репозитория:

| Пункт | Реальность |
|---|---|
| Конвертер второй биржи | **есть** — `bybit.py`, `binancefutures.py` |
| Снапшот на каждый актив | **есть** — `create_last_snapshot`, вызвать N раз |
| Задержка ордеров на биржу | **есть** — `feed_order_latency.py`, прогнать по каждой |
| Проверка пересечения диапазонов | ~20 строк numpy в тулинге |
| Правило парности `latency_offset`, тай-брейк `EventSet` | документация, 0 строк |

**Нового библиотечного кода — ноль.** Единственный настоящий блокер — что **у Hyperliquid нет
инкрементального стакана** (`AGENTS.md` §4.1a, `hyperliquid.py:66-72`). Отсюда следует не «делать
только сигнал», а «**вторая торгуемая биржа не должна быть HL**».

И прямо: **сигнальный вариант не даёт того, что было заказано.** Массив мидов из `bbo` — это не
стакан: ни глубины, ни очереди, ни исполнения на второй площадке. Если вопрос «могу ли я
котировать на обеих» — сигнальный путь на него не ответит никогда.

Поэтому развилка честная, и решает её **открытый вопрос 1**:

- **Исполняющая биржа — не HL** (Binance или Bybit торгуемая, HL как сигнал): делать сразу два
  актива. Нового кода нет, а сигнальный вариант был бы отсрочкой без выигрыша.
- **Исполняющая биржа — HL**: два торгуемых актива недоступны по вине фида биржи. Тогда
  сигнальный вариант — единственный честный, и стоит сначала им проверить, несёт ли вторая
  площадка информацию.

При двух торгуемых учесть: `EventSet::next` разрешает точные совпадения в пользу меньшего
`asset_no` (`evs.rs:43-63`); `exch_ts` двух бирж сравниваются как одно целое число, что
корректно только потому, что каждый встречается с глобальными часами через **свою** модель
задержки — стратегия не должна сравнивать биржевые таймстемпы двух активов, и это ничем не
проверяется; правило парности — если активу задан `latency_offset = X`, его источник задержки
ордеров обязан получить тот же `X` (`models/latency.rs:287-295` сдвигает `exch_ts += X`,
`resp_ts += 2X`), иначе фид виден с опозданием, а исполнения идут по старой задержке.

- **Фаза 0** — тесты зелёные, clippy без прироста, `fmt`. Для 0.1: остановить сеть на хосте и убедиться, что юнит уходит в `failed`, а не остаётся `active`. Для 0.4: запустить два инстанса на одну директорию одновременно и убедиться, что второй отказывает с именем и pid первого. Живой прогон с `kill -TERM`, `gzip -t` на всех файлах.
- **Фаза 1** — числа посчитаны по существующим `.gz` обеих бирж, в разбивке по каналам; правило применено письменно; результат в `collector/README.md`.
- **Фаза 2** — вторая биржа рядом с HL, обе пишут; попытка общей директории отвергается.
- **Фаза 3** — сдвиг из вывода конвертера зафиксирован для каждого файла; бэктест на первом дне данных не торгует по пустому стакану (проверить, что защита срабатывает).
