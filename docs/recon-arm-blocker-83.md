## 1. Дифф форка: что начато и на какой стадии брошено

**Ветка:** `fix/depth-freshness-83` = develop + ~20 чужих collector-коммитов (#74/#88;

**Механизм:** новый обязательный метод трейта `Bot` —
`depth_latency(asset_no) -> Option<(i64, i64)>` (`types.rs:1035+`): те же часы, что
`feed_latency`, но продвигаемые **только depth-кадрами**. Мотив записан в doc-комментарии
самого метода: `feed_latency` присваивается **выше** диспатча `event.is(..)`
(`live/bot.rs`), то есть его обновляет любой кадр, включая трейды, — площадка, у которой
книга замёрзла, а трейды печатаются, выглядит для него живой. Числа инцидентов вшиты в
доку: «Measured 2026-08-13 on the recorded HL tape: 111.7 s (2026-08-09) и 109.7 s (08-08)».

**Обе реализации `trait Bot` тронуты (§2 CLAUDE.md соблюдён):**

| Сторона | Где | Что штампует |

## 2. Guard-стек myhft: путь стухшей цены сейчас (по коду)

Читалось в worktree `~/myhft-liqguard` (= `feat/liquidation-guard-43`, ba03c8d, запушена).

**Где входят марки.** У бота единственная цена — его собственный стакан `LiveBot`
(строится только из инкрементальных вид-1 кадров, §4.1). Mid для #43 считается в
`drive_liquidation_guard` (`lib.rs:1973-1985`): `(best_bid+best_ask)/2` из `hbt.depth(0)`;
`None` только при односторонней книге (`INVALID_MIN`/`INVALID_MAX`). **Возраст mid не
проверяется нигде.** Единственный вход времени в #43 — возраст снапшота REST-поллера
(`max_staleness_ms`, дефолт 60 с, fail-closed) → `LiqVerdict::Stale`. Замёрзшая
двусторонняя книга даёт «валидный» mid любой давности, и гвард честно меряет дистанцию до
ликвидации по цене 110-секундной (или часовой) давности — **дыра (а) из задачи, ровно**.
Причём в этом состоянии не логируется ничего (`liquidation_guard_no_reading` требует
НЕчитаемого mid), значит вотчер #42 тоже слеп — ему нечего ловить.

**Существующий stale-feed guard** (`lib.rs:1017-1105`): post-ready, age =
`current_timestamp()` (= `Utc::now`, wall clock) − `feed_latency(0).local_ts`, порог
`max_feed_staleness_ms` (5000 в `example_config.toml`; live-конфиг не восстанавливался),
исход — `return Err(1)` = выход процесса = systemd-рестарт. Два ограничения:

1. ключуется на `feed_latency`, который обновляет **любой** Feed-кадр, включая трейды →
   «книга замёрзла, трейды идут» невидим. Ровно это чинит `depth_latency` из §1;
2. арминг skip-until-first-frame: снапшоты с `local_ts=0` не армят, НО HL-коннектор на
   регистрации переигрывает зеркало через `DepthMirror::restate`
   (`connector/src/hyperliquid/depth.rs:152`) **вид-1 событиями с `local_ts =
   local_now()`** — свежий штамп на замороженных данных. После рестарта бота против
   зависшего коннектора и `feed_latency`, и будущий `depth_latency` стартуют «свежими» и
   стухают лишь через порог. **Ловушка для спеки: свежесть по `local_ts` = свежесть
   транспорта, не данных; предел стухшести данных обеспечивает только дедлайн чтения на
   стороне коннектора.**

**Соседи:** loss-budget (#43-семейство) питается REST-поллером equity — независим от WS,
свой staleness 60 с; но он видит только убыток, не дистанцию. `FlattenPacer` — один на
процесс, триггер-агностичен; ему всё равно, кто попросил флэттен, — новый depth-гейт
может переиспользовать тот же рычаг.

**Что происходило в те ~110 с — по коду и по вытянутым до остановки хоста логам бота**
(wf_6cedb889: 45 часовых файлов `hl-bot-hype.2026-08-07-17 .. 09-13`, 946 976 строк,
0 unparseable):

- за 44 ч сессии: **38 `live_connection_interrupted_recoverable`, 38 `live_order_error`,
  3 `stale_feed_detected`** (тайминги этих трёх к дырам не привязаны — артефакты
  `fq-inputs` удалены, хост остановлен);
- **08-08, 109.72 с (08:34:23.506 → 08:36:13.2 UTC), venue-side:** WS reset 08:34:52,

## 3. WS-ридер коннектора HL: дедлайн чтения УЖЕ ЕСТЬ

Ключевая поправка к постановке задачи и к памятке venue-health («дедлайна на чтение
сокета нет ни в коллекторе, ни в connector/» — **неверно для connector/**, верно для
коллектора):

**`connector/src/hyperliquid/public_stream.rs`** (константы с doc-комментариями, есть с
Phase 1 `9da0e2a` — то есть стояли на проде 08-08/08-09):
- `IDLE_TIMEOUT = 90 s` — «No frame of any kind for this long means the socket is gone»;
  проверка каждые `IDLE_CHECK_INTERVAL = 15 s`; понги считаются кадрами (тихий рынок ≠
  полуоткрытый сокет);
- `PING_INTERVAL = 30 s` (app-level `{"method":"ping"}`→pong; venue сам рвёт за 60 с
  клиентской тишины); `WRITE_TIMEOUT = 10 s` (памятка в шапке: клинивший write однажды
  висел 15 часов); `CONNECT_TIMEOUT = 15 s`; backoff 1→30 с.
- `private_stream.rs` — те же константы, та же idle-ветка (строки 277-280).

**Следствие для (б):** структурный реконнект по тишине уже построен; вопрос спеки — не
«добавить дедлайн», а **пересогласовать бюджет**. Худший случай обнаружения зомби =
90 + 15 ≈ 105 с + ~1.2 с реконнект — это и есть масштаб обеих дыр. Гвард бота (5 с)
срабатывает в ~20 раз раньше, чем коннектор признаёт сокет мёртвым, а рестарт бота
коннектор не лечит (у бота нет рычага заставить коннектор переподключиться). При пинге
раз в 30 с здоровый сокет не молчит дольше ~30 с, так что дедлайн ~45–60 с (полтора-два
пропущенных понга) режет худший случай вдвое без ложных срабатываний по построению.

**Коллектор** (где обе дыры записаны): дедлайна чтения на сокете нет; сторожа —
`watchdog.rs` (тотальная тишина по **записям**, 5 мин, стоп) и `liveness.rs` (per-symbol,
60 с, только warn). Зомби 08-09 закончился только kernel reset. Отдельная дыра
измерительного контура; арм не блокирует.

**Прецедент в этом же репо:** Lighter-коннектор, коммит `d107022` — 120-с watchdog
тишины книги → `Concern::Silent` → структурный repair (unsubscribe/subscribe, кулдаун
60 с/маркет, эскалация в `Unacknowledged` если repair проглочен). Образец «тишина
чинится, а не только рапортуется» для спеки.
