# Design: мульти-коннекторный `LiveBot` — изоляция батчей и происхождение ошибок

Статус: **v2 + P0 реализован** (2026-08-05, ветка `feat/multi-connector-hardening`, четыре коммита
от `45c0e1e`). Разделы 1–10 — дизайн как он был написан; **§11 внизу — что реально поехало и чем
оно отличается от v2**. Там же три места, где реализация сознательно разошлась с нотой; при
расхождении текста §1–10 с §11 побеждает §11 и код.
Ветка: `feat/multi-connector-hardening` (от `develop`).

**История ревизий.** v1 прошёл ревью (`wm3c8emah`): вердикт «sound with fixes», **механизм подтверждён**
— заполнять существующий `usize`-слот приёмника представительным `inst_no` коннектора-источника,
`BotError` держать вне провода. v2 не переделывает механизм; он чинит два блокера и четыре мажора
ревью, и две правки из них **упрощают** дизайн:

| Что изменилось в v2 | Почему |
|---|---|
| **Все** гейты возврата — единообразный `any_open` (§3.3) | v1 делал гейты подавления результата per-connector, а гейт длительности — `any`. Ревью доказало, что асимметрия **сама по себе рвёт торгуемую книгу**: чужой `Feed` проходит свой per-connector гейт и возвращает управление стратегии, пока батч HL открыт. Заодно исчезла асимметрия, которую надо было объяснять. |
| Потолок удержания — **P0**, не P1 (§3.4, §7) | С единообразным `any_open` осиротевший `BatchStart` **вешает** `elapse` до потолка — хуже, чем сегодня, где любой `BatchEnd` снимает единственный глобальный флаг. Потолок не «желателен после», он обязателен **в той же фазе**. |
| Третья дорога отказа — `Channel::send` (§2.2, §4.1) | Отказ отправки тоже безымянный, а `heartbeat` шлёт **в каждый** коннектор: провал отправки в Binance убивает торговлю на HL. v1 этой дороги не видел. |
| `deferred: Option<(usize, ElapseResult)>` → обратно `wait_resp_received: bool` (§3.2) | При `any_open`-освобождении ключ коннектора в отложенном результате не используется ничем. Однослотовая перезапись, которую отметило ревью, исчезает вместе с полем. |
| Батч-глубина `Vec<u32>` вместо `Vec<bool>` (§3.2, §3.6) | Вложенность батчей **внутри одного** коннектора реальна и читается в коде коннектора (регистрационный батч приезжает внутрь маркет-дата-батча). v1 её не упоминал вовсе. |
| §8 переписан по **реальному** дереву `myhft` | v1 утверждал, что рейт-лимит-классификатор и `record_critical` «остаются как есть». Это неверно: они оба — дороги к `return Err(1)`, и оба origin-blind. Ниже перечислены **все** пути от ошибки до выхода процесса с `файл:строка`. |
| Обязательство при терпимости дороги 1/3 (§4.3) | `BotError` из `recv` **обрывает** `elapse` (`bot.rs:462-464`), в отличие от терпимого `LiveError`, который продолжает цикл. Потребитель, который терпит, обязан это учитывать. |
| Тест, привязывающий origin к **опрошенному каналу** (§6.2) | Чистая `attribute()` пинит атрибуцию события, но ничто не пинит, что `origin_inst_no` принадлежит именно тому каналу, который опросили — ровно провал §4.2 `AGENTS.md` (зелёный пин над недоказанной атрибуцией). |

wire-протокола), §4.1 (какие depth-события `LiveBot` вообще применяет), §4.7 (что `LiveBot` ведёт в

## 1. Зачем

Сегодня `myhft` регистрирует **ровно один** инструмент: `LiveBotBuilder::new().register(instrument)`
[код-bot `src/main.rs:25`, `:40` — два билдера, оба с одним `register`; единственный `Instrument::new`
— `src/main.rs:296-303`]. Задача #20 step 4 («перенос режима A — Binance-сигнал — в живой бот»)
добавляет **второй** коннектор: market-data-only Binance рядом с торговым Hyperliquid. Оба дефекта
ниже в одно-коннекторной конфигурации ненаблюдаемы и оба становятся money-path ровно на этом шаге.

Обе половины хардненинга **не трогают провод**: ни `LiveEvent`, ни `LiveRequest`, ни `ErrorKind`, ни
`CustomHeader`, ни bincode-раскладку. Это главный вывод дизайна и он не случайный — см. §2.3.

## 2. Что именно ломается

### 2.1 Batch tear: `batch_mode` — один `bool` на все коннекторы

`elapse_` держит **одну** переменную `let mut batch_mode = false` [код `live/bot.rs:404`], которую
ставит любой `BatchStart` [код `:411`] и снимает любой `BatchEnd` [код `:414`]. Оба варианта приходят
**без символа и без имени коннектора** — это unit-варианты `LiveEvent` [код `types.rs:129,130`], и
`IceoryxUnifiedChannel::recv_timeout` отдаёт их с жёстко зашитым нулём:

```rust
// hftbacktest/src/live/ipc/iceoryx.rs:350-353
LiveEvent::BatchStart | LiveEvent::BatchEnd | LiveEvent::Error(_) => {
    // todo: it may cause incorrect usage.
    return Ok((0, ev));
}
```

а `elapse_` этот `usize` для батч-вариантов **выбрасывает**: `Ok((_, LiveEvent::BatchStart))`
[код `:410,413`]. Комментарий `// todo: it may cause incorrect usage` — апстримное признание ровно
этой дыры.

**Перемешивание батчей — не редкая гонка, а свойство конструкции приёмника.** `recv_timeout`
опрашивает **один** канал за итерацию и сразу сдвигает курсор:

```rust
// iceoryx.rs:337-342
let ch = unsafe { self.unique_channel.get_unchecked(self.ch_i) };
self.ch_i += 1;
if self.ch_i == self.unique_channel.len() { self.ch_i = 0; }
```

Каналы заведены **по имени коннектора** [код `iceoryx.rs:291-315` — `HashMap<String, IceoryxChannel>`
с ключом `instrument.connector_name`], то есть при двух коннекторах round-robin **гарантирует**
чередование 1:1, пока в обоих есть сообщения. Батч у всех бэкендов — это один venue-кадр целиком:
`publish()` у HL шлёт `BatchStart` → N `Feed` → `BatchEnd` [код `connector/src/hyperliquid/public_stream.rs:652-658`],
Binance так же на каждый `depthUpdate` [код `connector/src/binancefutures/market_data_stream.rs:203,241`
и `:286,324`], и всё это уходит `TO_ALL` (`dst_id = 0`), то есть каждому боту. Плюс регистрационный
батч `BatchStart` → orders/position/depth-snapshot → `BatchEnd` → `SnapshotComplete`
[код `connector/src/main.rs:339-391`].

Отсюда два следствия, оба реальные:

- **(a) `batch_mode == false` посреди HL-батча.** HL открыл батч, Binance закрыл свой →
  флаг снят → следующее HL-событие проходит гейт `if !batch_mode` [код `:431`/`:437`] и `elapse`
  возвращает управление стратегии **на полуприменённом кадре HL**. Стратегия читает книгу, на которой
  квотирует, в разорванном виде. Тот же путь у гейта по длительности [код `:474`].
  Отдельный подслучай: `if wait_resp_received { return Ok(ElapseResult::Ok) }` на `BatchEnd`
  [код `:417`] — **чужой** `BatchEnd` возвращает управление, причём с результатом `Ok`, а не с
  отложенным `MarketFeed`/`OrderResponse`.
- **(b) `batch_mode == true` посреди HL-применения.** HL свой батч закрыл, Binance открыл свой →
  гейт `:474` не пускает `elapse` вернуться, и это тянется на всё время дренажа чужого батча.
  Для мейкера «не могу вернуть управление» = «не могу перекотироваться», то есть тоже деньги.
  Дренаж 200-уровневого снапшота Binance — это ~400 отдельных iceoryx-сообщений [вывод из
  `market_data_stream.rs:286-324` — по сообщению на уровень].

**(a) и (b) — не равноценны, и v2 выбирает сторону явно.** (a) — разорванная книга под квотирующей
стратегией; (b) — задержка возврата. Первое стратегия не может ни увидеть, ни исправить; второе
ограничивается сверху (§3.4) и наблюдаемо в логе. Поэтому v2 лечит (a) полностью и **сознательно
оставляет (b) с потолком** — v1 пытался вылечить оба и получил дыру в (a), см. §3.3.

**Важное уточнение терминологии.** `batch_mode` **не буферизует применение**. Все события
применяются в стакан по мере прихода [код `live/bot.rs:257-276`]; батч откладывает только *возврат
управления стратегии*. То есть «атомарность батча» здесь — это «стратегия не увидит промежуточное
состояние», а не «стакан не побывает в промежуточном состоянии». Настоящая apply-буферизация — это
другой, больший дизайн (§3.7, отклонено на P0).

### 2.2 Ошибка чужого коннектора останавливает торговлю HL

**Три** дороги, все безымянные. Третью v1 не видел; она найдена ревью и подтверждена чтением.

**Дорога 1 — `BotError` из приёма, минуя `error_handler` вообще.** Отказ `receive()` на *любом* из
каналов превращается в анонимную строку:

```rust
// iceoryx.rs:344-346
if let Some((dst_id, ev)) = ch.receive()
    .map_err(|err| BotError::Custom(err.to_string()))?
```

`ChannelError` покрывает `Decode` (bincode), `ReceiveError`, `FromUtf8` [код `iceoryx.rs:41-57`].
В `elapse_` это уходит в `Err(error) => return Err(error)` [код `:462-464`] — **`error_handler` не
вызывается**. А потребитель считает любой `Err` из `elapse` фатальным:

```rust
// myhft/src/lib.rs:419-436 [код-bot]
match hbt.elapse(elapse_duration) {
    Ok(ElapseResult::Ok) => {}
    Ok(result) => { error!(event = "live_loop_stopped", ...); return Err(1); }   // :427
    Err(err)   => { error!(event = "live_loop_error",  ...); return Err(1); }    // :435
}
```

`return Err(1)` → `std::process::exit(1)` [код-bot `main.rs:378-383`] → супервизор перезапускает. То
есть **decode-ошибка на Binance-канале убивает процесс, который торгует на HL**. И она не одноразовая:
при рассинхроне версий (коннектор новее бота — §2 `AGENTS.md`) недекодируемым будет **каждое**
сообщение того канала, то есть получается restart-loop бота, который на HL был полностью здоров
[вывод].

**Дорога 2 — `LiveEvent::Error` без происхождения.** `LiveError { kind, value }` [код `types.rs:92-97`]
едет к `error_handler` [код `bot.rs:323-327`], и в нём нет ничего, что отличало бы HL от Binance.
Потребитель обязан решать фатальность по одному `ErrorKind`:

```rust
// myhft/src/lib.rs:282-294 [код-bot] handle_live_error
ErrorKind::ConnectionInterrupted => { error!(...); Err(BotError::Interrupted) }  // :286 фатально
ErrorKind::CriticalConnectionError => Ok(()),                                    // :293 решает breaker
```

`ConnectionInterrupted` публикуют **все** бэкенды на разрыв стрима [код `bybit/mod.rs:171,188,195,225,273`,
`binancefutures/mod.rs:131,169`, HL через `publish_error`]. Значит обычный реконнект market-data-only
Binance даёт `Err(BotError::Interrupted)` из хендлера → `process_event` пробрасывает `?`
[код `bot.rs:325`] → `elapse_` пробрасывает `?` [код `:422`] → `elapse` вернёт `Err` →
`return Err(1)` → **HL перестаёт торговать из-за чужой маркет-даты**.

**Дорога 3 — отказ `Channel::send`, и он бьёт по всем коннекторам сразу.** Отправка тоже теряет имя:

```rust
// iceoryx.rs:372-378
fn send(&mut self, id: u64, inst_no: usize, request: LiveRequest) -> Result<(), BotError> {
    self.channel.get(inst_no).ok_or(BotError::InstrumentNotFound)?
        .send(id, &request)
        .map_err(|err| BotError::Custom(err.to_string()))?;   // :377 — анонимно
```

Само по себе это было бы локально (отправка адресована конкретному `inst_no`), если бы не heartbeat:
`LiveBot::heartbeat` шлёт **в каждый инструмент, то есть в каждый коннектор**, и любой отказ
пробрасывается:

```rust
// bot.rs:363-366
for inst_no in 0..self.instruments.len() {
    self.channel.send(self.id, inst_no, LiveRequest::Heartbeat)?;
}
```

`heartbeat` вызывается из `elapse_` трижды — на входе [код `:401`], в таймаут-ветке [код `:448`] и в
конце итерации цикла [код `:471`], — и везде через `?`. Значит **провал отправки в market-data-only
Binance даёт `Err` из `elapse`, то есть тот же `return Err(1)` и ту же остановку торговли на HL**
[вывод, цепочка целиком читается]. Дорога 3 лечится ровно так же, как дорога 1: `BotError::Channel`
с именем коннектора (§4.1), которое канал знает и сегодня выбрасывает.

**Смежное, вне scope.** `node.wait(..)` → `Err` даёт `BotError::Interrupted` [код `iceoryx.rs:365-367`]
→ `ElapseResult::EndOfData` [код `bot.rs:459-461`] → у потребителя `Ok(result)`-ветка
[код-bot `lib.rs:421-427`] → тот же `return Err(1)`. Эта дорога **не** per-connector (node общий на
процесс), её мы не трогаем — §10.

### 2.3 Ключевое наблюдение: происхождение уже есть, его дважды выбрасывают

`recv_timeout` **уже** возвращает `usize` рядом с событием [код `ipc/mod.rs:20-27` — контракт
`(instrument_no, LiveEvent)`], и приёмник **знает** источник: он только что опросил конкретный
`IceoryxChannel`, а канал — это ровно один коннектор по построению [код `iceoryx.rs:291-315`].
Происхождение теряется не на проводе, а **на приёмной стороне, в двух строках**: `Ok((0, ev))`
[код `iceoryx.rs:352`] и `Ok((_, LiveEvent::BatchStart))` [код `bot.rs:410`]. У дороги 3 то же самое:
`self.channel.get(inst_no)` [код `iceoryx.rs:373`] возвращает тот самый канал, чьё имя нужно.

Поэтому весь этот хардненинг — **wire-free**. Ни один коннекторный бинарь пересобирать не нужно;
старые задеплоенные коннекторы (bybit / HL / lighter / binance) работают с новым ботом без изменений.
Это прямая противоположность обычному «обновляются парой» из §2 `AGENTS.md`, и это надо явно
проверить в ревью: любой вариант дизайна, требующий B-класса, слабее по построению, потому что тот же
факт уже доступен бесплатно.

## 3. Решение 1: изоляция батчей по коннектору

### 3.1 Контракт возвращаемого `usize`

Единственное изменение канала: для «безсимвольных» вариантов (`BatchStart`, `BatchEnd`, `Error`)
вернуть **валидный `inst_no`, принадлежащий коннектору-источнику**, вместо константного нуля.

```rust
// iceoryx.rs — IceoryxChannel получает два поля, оба вычисляются при build
pub struct IceoryxChannel<S, R> {
    publisher: IceoryxSender<S>,
    subscriber: IceoryxReceiver<R>,
    symbol_to_inst_no: HashMap<String, usize>,
    name: String,          // имя коннектора: сегодня его канал не помнит [код `iceoryx.rs:210-214`]
    origin_inst_no: usize, // минимальный зарегистрированный inst_no этого канала
}
```

Почему именно «представительный `inst_no`», а не индекс коннектора:

- **Смысл поля остаётся один и тот же.** Контракт становится «этот `usize` — всегда валидный индекс в
  `instruments`, и всегда такой, чей коннектор породил событие». Индекс коннектора в том же слоте — это
  **новый источник `inst_no`**, а `process_event` индексирует `instruments` через
  `get_unchecked_mut(inst_no)` [код `bot.rs:258,287,319,329`]. §2 `AGENTS.md` прямо запрещает
  расширять `unsafe`: «если добавляешь новый источник `inst_no` — либо докажи инвариант, либо используй
  безопасный доступ». Представительный `inst_no` инвариант **усиливает** (сегодня `0` валиден, но
  «не тот»), индекс коннектора — ломает.
- **Не появляется нового неявного инварианта между структурами.** Индекс коннектора потребовал бы,
  чтобы порядок `unique_channel` [код `iceoryx.rs:262-272`] совпадал с порядком, который бот выведет
  сам из `instruments` — согласование через два независимых кода, то есть ровно «неявная магия»,
  запрещённая §1.5.
- **Детерминизм и дешевизна.** `origin_inst_no` считается один раз в `register` [код `iceoryx.rs:232-238`],
  на приёме — ноль работы.

Контракт дописывается в doc `Channel::recv_timeout` [код `ipc/mod.rs:20-27`]; **подпись не меняется**,
поэтому сторонние реализации `Channel` продолжают компилироваться, а те, что возвращают `0` (как
`MockChannel`/`QuietChannel` в тестах [код `bot.rs:826,866`]), ведут себя ровно как сегодня — то есть
корректно для одно-коннекторного случая, который у них и есть.

**Проверка входа `process_event` — настоящая, а не `debug_assert`.** v1 предлагал
`debug_assert!(inst_no < self.instruments.len())`. Это было бы **инертно в проде**: корневой
`Cargo.toml` держит `debug-assertions = false` и в `[profile.release]` [код `Cargo.toml:32`], и — что
менее очевидно — в `[profile.dev]` [код `Cargo.toml:13`]; включены они только в `[profile.test]`
[код `Cargo.toml:23`]. Ассерт сработал бы ровно в `cargo test` и ни разу у бота, который к тому же
собирается с `panic = "abort"` [код `Cargo.toml:35`]. Поэтому вместо ассерта — обычная проверка в
начале `process_event`:

```rust
if inst_no >= self.instruments.len() {
    error!(%inst_no, len = self.instruments.len(), "Channel returned an out-of-range inst_no");
    return Err(BotError::InstrumentNotFound);
}
```

Одно сравнение на событие в пути, где и так есть `HashMap`-лукапы, и после него все существующие
`get_unchecked_mut` в этой функции **доказуемо** в границах, причём доказательство локально — не
разъезжается по двум файлам, как сегодня. Это же покрывает и новый индекс `conn_of_inst[inst_no]`
из §4.1.

### 3.2 Состояние в `LiveBot`

```rust
pub struct LiveBot<CH, MD> {
    // ...
    /// Индекс коннектора для каждого inst_no. Порядок — первое появление
    /// `connector_name` в `instruments`; вычисляется один раз в build.
    conn_of_inst: Vec<usize>,
    /// Имена коннекторов в том же порядке (нужны и §4 для атрибуции ошибок).
    connector_names: Vec<String>,
    /// Глубина открытых батчей у коннектора c. Сбрасывается в начале каждого elapse_.
    batch_depth: Vec<u32>,
}
```

Никаких `Arc`/`Mutex`: владелец один, писатель один — §1.4 соблюдён. Аллокаций в hot path нет:
`batch_depth` живёт в структуре и в начале `elapse_` делается `fill(0)` — это ровно та же
семантика, что у сегодняшнего `let mut batch_mode = false` [код `:404`], только векторная.

Два решения, которые v2 принимает явно:

- **`Vec<u32>`, а не `Vec<bool>` — из-за вложенности внутри одного коннектора (§3.6).** Стоимость —
  тот же вектор, `saturating_add(1)` / `saturating_sub(1)` вместо присваивания.
- **`wait_resp_received: bool` остаётся ровно таким, как сегодня** [код `:405`]. v1 менял его на
  `deferred: Option<(usize, ElapseResult)>`; при единообразном `any_open`-освобождении (§3.3) ключ
  коннектора в отложенном результате **не читается никем**: условие выпуска — «нигде не открыт батч»,
  а не «закрылся батч именно того коннектора». А раз §10 сознательно сохраняет варт
  «`BatchEnd` → `Ok(ElapseResult::Ok)`», то и сам `ElapseResult` в слоте хранить незачем. Однослотовая
  перезапись (что делать, если отложены и `MarketFeed`, и `OrderResponse`), которую отметило ревью,
  исчезает вместе с полем: `bool` идемпотентен, и поведение остаётся сегодняшним.

### 3.3 Гейты: все возвраты — единообразный `any_open`

Вспомогательное: `fn any_batch_open(&self) -> bool { self.batch_depth.iter().any(|&d| d > 0) }`.

| Гейт | Сегодня [код] | Становится |
|---|---|---|
| `BatchStart` | `batch_mode = true` `:411` | `batch_depth[conn_of_inst[inst_no]] += 1` (saturating) |
| `BatchEnd` | `batch_mode = false` `:414` | `batch_depth[c] -= 1` (saturating), где `c = conn_of_inst[inst_no]` |
| ранний возврат на `BatchEnd` | `if wait_resp_received` `:417` | `if wait_resp_received && !any_batch_open()` |
| `MarketFeed` | `if !batch_mode` `:431` | `if !any_batch_open()` |
| `OrderResponse` | `if !batch_mode` `:437` | `if !any_batch_open()` |
| конец по длительности | `if !batch_mode && elapsed > duration` `:474` | `if !any_batch_open() && elapsed > duration` (+ потолок §3.4) |

**Почему единообразно, и почему v1 здесь ошибался.** v1 делал первые три гейта per-connector
(«отложенный результат принадлежит конкретному инструменту, чужой батч к нему не относится»), а
гейт длительности — `any`. Рассуждение звучало, но проверялось не то: гейт решает не «чей результат
вернуть», а **«можно ли отдать стратегии управление»**. Возврат управления — это не выдача одного
кадра, это разрешение стратегии прочитать **все** книги, позицию и ордера. Контрпример ревью
воспроизводится по строкам: HL прислал `BatchStart` (`batch_open[0] = true`), Binance прислал `Feed`
(`inst_no = 1`, `batch_open[1] == false`) → per-connector гейт `:431` пропускает → `elapse` вернулся →
стратегия читает **полуприменённую книгу HL**. То есть асимметрия сохраняла ровно тот тир (a), ради
которого весь дизайн, и делала это на самом опасном пути — торговой книге.

Единообразный `any_open` устраняет и асимметрию, и её обоснование:

- Правило одно и формулируется одной фразой: **пока хоть где-то открыт батч, управление не
  возвращается**. Ни зависимости от порядка прихода, ни двух разных ответов на вопрос «почему тут
  можно, а там нельзя».
- Цена — (b): чужой открытый батч задерживает наш возврат, включая ожидание ответа на собственный
  ордер (`submit_order(wait = true)` / `Bot::cancel` — 60 с, зашитые в `submit_order`). Задержка
  ограничена сверху двумя вещами: round-robin не даёт голодания (чужой `BatchEnd` придёт через ≤ N
  итераций приёма, пока чужой коннектор жив), а на случай, когда он **не** жив, есть потолок §3.4.
  Именно поэтому потолок в v2 переехал в P0: без него единообразный `any_open` строго хуже
  сегодняшнего поведения на осиротевшем `BatchStart`.
- Per-connector состояние при этом **никуда не девается** и нужно по трём причинам, ни одна из
  которых не про правило выпуска: (1) чужой `BatchEnd` не должен снимать наш `BatchStart` — это и есть
  тир (a); (2) лог потолка должен называть **застрявший** коннектор, иначе оператор смотрит в
  «где-то что-то открыто»; (3) тот же `conn_of_inst` обслуживает §4.

**Следствие для честности дизайна, которое надо назвать вслух.** Раз правило выпуска глобальное,
«счётчик на весь бот» (§3.7) даёт **то же самое** наблюдаемое поведение на корректном потоке. Разница
появляется только на нарушении протокола: при глобальном счётчике лишний `BatchEnd` болтливого
market-data-коннектора декрементирует **чужой** открытый батч, а при per-connector — ущерб остаётся
внутри неисправного коннектора. Мы выбираем per-connector именно из-за этого свойства локализации
(и из-за (2)–(3) выше), а не потому, что без него правило выпуска не сформулировать.

### 3.4 Осиротевший `BatchStart` и потолок удержания — **P0**

Дефект существует **уже сегодня** и с одним коннектором: потерянный `BatchEnd` оставляет `batch_mode`
навсегда `true`, и на занятом фиде `elapse` не вернётся никогда — гейт `:474` не пускает, а
`Err(BotError::Timeout)`-выход [код `:443-458`] на занятом фиде не наступает, потому что таймаут
приёма истекает только когда весь чанк прошёл без сообщений. Бот при этом **продолжает
heartbeat-ить** изнутри цикла [код `:448,471`], то есть коннектор его не сметёт: получается тихо
неквотирующий, но «живой» бот.

**Почему это P0, а не P1 (исправление самопротиворечия v1 §7).** Сегодня единственный глобальный флаг
снимает **любой** `BatchEnd` — то есть болтливый второй коннектор случайно «лечит» осиротевший
`BatchStart` первого (криво, тиром, но `elapse` возвращается). После §3.3 этого лекарства нет по
построению: чужой `BatchEnd` больше не трогает чужую глубину, а `any_open` держит возврат.
Значит **изоляция без потолка делает осиротевший `BatchStart` строго хуже, чем до неё**. Нельзя
поставить первую половину в P0, а вторую в P1: между ними живёт регрессия. Обе — одна фаза.

```rust
if elapsed > duration {
    if !self.any_batch_open() { return Ok(ElapseResult::Ok); }
    let now = instant + elapsed;                       // переиспользуем чтение, как heartbeat
    let started = *hold_started.get_or_insert(now);
    if now.saturating_duration_since(started) > self.max_batch_hold {
        warn!(open = ?self.open_connector_names(), "A batch has held this elapse past its \
               ceiling; returning on a possibly torn book rather than never returning.");
        return Ok(ElapseResult::Ok);
    }
}
```

Направление отказа выбрано осознанно и это **не** нарушение §1.1, а её применение: разорванное чтение
книги-сигнала самолечится следующим кадром и видно stale-guard-у потребителя, а навсегда зависший
`elapse` — это бот, который перестал управлять деньгами и об этом молчит. Из двух «закрытых» позиций
хуже вторая.

`max_batch_hold` — приватное поле со значением из `const MAX_BATCH_HOLD`, без builder-опции: это
защита от нарушения протокола, а не торговая политика (§1.1 запрещает второе, не первое). Тесты
выставляют поле напрямую — так уже сделано с `heartbeat_interval` [код `bot.rs:1132,1146,1202`].
**Само число — открытый вопрос §9.1**, потому что время дренажа самого большого реального батча в
репозитории не измерено (бенчмарков нет — §5 `AGENTS.md`). Ограничение сверху жёсткое: потолок должен
быть заметно меньше и 10-секундного окна живости коннектора, и 5-секундного stale-гейта бота
[код-bot `lib.rs:414-415`], иначе он не потолок, а декорация.

### 3.5 Одно-коннекторный случай

При одном коннекторе `batch_depth` — вектор длины 1, `conn_of_inst` — все нули, и:
`any_batch_open()` ≡ `batch_mode`; гейты `:431`/`:437`/`:417` ≡ сегодняшние; значение возврата на
`BatchEnd` остаётся `ElapseResult::Ok` (см. §10 — это wart, который мы **сохраняем** ради этой
эквивалентности).

Расхождения ровно два, оба намеренные и оба пинятся отдельно:

1. **§3.4**: там, где сегодня зависание, теперь возврат по потолку.
2. **Вложенный батч** (§3.6): сегодня внутренний `BatchEnd` снимает флаг и рвёт внешний батч; со
   счётчиком — не снимает. Это тоже изменение поведения на одном коннекторе, и оно тоже в сторону
   «меньше тира».

«Bit-identical» тестом не доказывается; доказуемо — поведенческое равенство на скриптованных
трассах **со сбалансированными невложенными батчами**, и на это есть дифференциальный тест §6.4.

### 3.6 Вложенность и внутриконнекторный остаток

**Вложенность внутри одного коннектора реальна, и v1 её не упоминал.** Батч маркет-даты уходит
несколькими отдельными сообщениями в общий mpsc (`PublishEvent::BatchStart` → N событий →
`PublishEvent::BatchEnd` [код `hyperliquid/public_stream.rs:652-658`]), а регистрационный батч
формируется **целиком внутри одного** `handle_msg` [код `connector/src/main.rs:339-391`]. Publish-таск
разбирает очередь по одному сообщению, поэтому регистрационный батч может лечь **между** `BatchStart`
и `BatchEnd` маркет-дата-батча того же коннектора:

```
BatchStart(md) … Feed … [BatchStart(reg) … BatchEnd(reg) SnapshotComplete] … Feed … BatchEnd(md)
```

[вывод из двух call-site-ов выше — читается, не измерено]. С `Vec<bool>` внутренний `BatchEnd` снял бы
флаг и вернул управление посреди внешнего батча — тот же тир (a), только внутри одного коннектора, и
происходило бы это **на каждой регистрации**, то есть на старте бота, который как раз собирается
квотировать. `Vec<u32>` закрывает это по построению: 1 → 2 → 1 → 0.

Что счётчик **не** закрывает и что остаётся известным остатком: несбалансированный поток. Лишний
`BatchEnd` уходит в `saturating_sub` и пропадает молча (fail-safe в сторону «возврат возможен»),
лишний `BatchStart` держит глубину — и его ловит только потолок §3.4. Различить «вложенный батч» и
«потерянный маркер» приёмник не может: на проводе они одинаковы, оба маркера — unit-варианты.

**Изоляция — по коннектору, не по инструменту.** У HL с 16 монетами на одном коннекторе батч кадра BTC
задерживает возврат по ETH: батчи публикуются на весь коннектор [код `hyperliquid/public_stream.rs:652`],
символа в маркере нет. При единообразном `any_open` (§3.3) это даже не «остаток per-connector-подхода»,
а прямое следствие правила: **любой** открытый батч где угодно задерживает возврат везде. Для
конфигурации #20 step 4 (1 символ HL + 1 символ Binance) гранулярность достаточная; per-instrument
потребовал бы символ в маркере, то есть класс B — §3.7.

### 3.7 Отклонённые альтернативы

| Альтернатива | Почему нет |
|---|---|
| **Глобальный счётчик батчей** (`+1`/`-1`, `batch_mode = count > 0`) | Самый честный runner-up, и после §3.3 разрыв сузился: на корректном потоке наблюдаемое поведение **совпадает**. Отличается на нарушении протокола — лишний `BatchEnd` одного коннектора декрементирует открытый батч другого, то есть чужая болтовня снова умеет рвать нашу книгу, — и ничего не даёт §4 (атрибуции нет) и потолку (лог не назовёт застрявшего). Дешевле на один `Vec`, слабее там, где мы как раз собираемся терпеть чужие неисправности. |
| **Сериализовать коннекторы** (дренировать канал до `BatchEnd`, потом переключаться) | Голодание: пока A внутри батча, B не читается вовсе; потерянный `BatchEnd` у A запирает B навсегда. И head-of-line blocking ордерных ответов торгового коннектора за снапшотом маркет-даты. Ломает fairness приёма для всех, включая одно-коннекторных. |
| **Символ/имя коннектора в маркерах батча на проводе** (`BatchStart { symbol }`) | Класс B, и **дороже, чем оценивал v1**: это не append-only. `BatchStart`/`BatchEnd` — варианты **0 и 1** `LiveEvent` [код `types.rs:129-130`], добавление поля меняет полезную нагрузку уже существующего дискриминанта, то есть жёсткий парный апгрейд **без** окна совместимости (старый бот прочтёт новый кадр как мусор, а не как «неизвестный вариант»). Плюс байты в 512-байтовый лимит на каждый маркер. Даёт больше (per-instrument изоляцию), но дороже того, что уже доступно бесплатно (§2.3), и не помогает ни дороге 1, ни дороге 3 §2.2, ни старым задеплоенным коннекторам. Отложено до момента, когда реально понадобится per-instrument (§9.5). |
| **`Arc`/`Mutex` на состояние батча** | §1.4: второго писателя нет, а появление `Arc` в процессе бота — прямое нарушение красной линии. |
| **Настоящая apply-буферизация сейчас** (складывать `Feed` в staging, применять на `BatchEnd`) | Структурно это *лучший* конечный ответ: возврат в любой момент безопасен по построению, гейт `:474` перестаёт нуждаться в батче вовсе, осиротевший `BatchStart` стоит «книга C не обновляется» (громко, ловится stale-guard-ом) вместо зависания, и (b) исчезает вместе с потолком. Но: **не** bit-identical (меняется момент видимости обновлений, `last_feed_latency` [код `:259`], порядок `last_trades` [код `:271`]), нужен буфер на коннектор, и это отдельный дизайн с собственным ревью. P2 — §7. |
| **Батч-состояние, живущее между вызовами `elapse`** (в структуре, без сброса) | Строго говоря батч — свойство потока, а не вызова. Но выгода маргинальна: раз `Timeout`-выход [код `:451`] уже возвращает управление посреди батча, разрыв к тому моменту уже случился; помнить его — значит только задержать *следующий* возврат. Сохраняем per-call сброс ради §3.5, остаток документируем (§10). |

## 4. Решение 2: происхождение ошибки

### 4.1 Решение: штампует получатель, а не отправитель

Все три дороги §2.2 получают имя коннектора **на приёмной стороне**, из того же факта, что и §3:
канал знает, кого он опросил или кому не смог отправить.

- **Дороги 1 и 3.** `iceoryx.rs:344-346` (приём) и `iceoryx.rs:372-378` (отправка) перестают отдавать
  анонимную строку:

  ```rust
  #[derive(Error, Debug)]
  pub enum BotError {
      // ... существующие варианты не тронуты ...
      #[error("Channel({connector}): {message}")]
      Channel { connector: String, message: String },
  }
  ```

  Имя берётся из нового поля `IceoryxChannel::name` (§3.1) — у приёма это опрошенный канал, у отправки
  тот, что вернул `self.channel.get(inst_no)` [код `iceoryx.rs:373`]. `BotError` **не на проводе**
  (нет `Encode`/`Decode` — [код `bot.rs:38-54`]), поэтому это класс A. Политику **не тащим в
  библиотеку**: `elapse_` по-прежнему возвращает `Err` [код `:462-464`], а решает потребитель — ровно
  то разделение, которое §1.1 `AGENTS.md` требует. У `myhft` для этого уже есть место: ветка
  `Err(err)` в цикле [код-bot `lib.rs:429-435`].

- **Дорога 2.** `ErrorHandler` получает имя источника:

  ```rust
  pub type ErrorHandler = Box<dyn Fn(&str, LiveError) -> Result<(), BotError>>;
  ```

  Имя берётся как `&self.connector_names[self.conn_of_inst[inst_no]]` в `Error`-ветке
  `process_event` [код `bot.rs:323-327`] — то есть из того же `usize`, что и §3. Одно изменение
  приёмника обслуживает обе фичи.

Библиотека при этом **не решает**, что делать с heartbeat-ом, который не доехал до market-data-only
коннектора. Она называет коннектор; политику («в этот коннектор мы всё равно не торгуем») задаёт
потребитель — §8.3, путь 4.

### 4.2 Почему меняем подпись, а не добавляем второй хендлер

Аддитивный вариант (`error_handler` как есть + новый `error_handler_with_origin`) не ломает никого,
но допускает конструкцию, при которой после пин-бампа `myhft` оставляет старый хендлер, **не получает
происхождения и продолжает валить HL на реконнекте Binance** — то есть баг, который мы починили,
уезжает в прод зелёным. Смена подписи делает миграцию невозможной к забыванию: это ошибка
компиляции, одна строка. Стоимость ровно та же, что и польза, потому что #20 step 4 обязан править
этот хендлер в любом случае. §7 `AGENTS.md` ставит простоту (3) выше upstream-совместимости (5), и
здесь оба аргумента совпадают: один хендлер, один смысл.

### 4.3 Обязательства потребителя: терпимость покупается двумя вещами

**Это часть дизайна, а не совет.** Терпимость к чужой ошибке — не бесплатная операция; она меняет
громкий отказ на тихий, и потребитель обязан закрыть обе образовавшиеся дыры.

**(1) Stale-гейт на терпимую книгу.** Как только ошибка market-data-коннектора становится нефатальной,
Binance-книга может замереть, а стратегия продолжит считать по ней сигнал и квотировать на HL.
У `myhft` stale-feed guard существует и настроен на 5 с [код-bot `lib.rs:414-415`,
`max_feed_staleness_ms`], но он смотрит **только на asset 0** [код-bot `lib.rs:479` —
`hbt.feed_latency(0)`]. Расширение на asset 1 (сигнальный) — обязательное условие включения
терпимости, и без него #20 step 4 хуже, чем сегодняшнее «падать и рестартовать».
Заодно напоминание из §4.7 `AGENTS.md`: `depth.timestamp` для этого читать нельзя (он никогда не
пишется), источник — `feed_latency(asset_no)` [код `bot.rs:789-791`].

**(2) Терпимость к дороге 1/3 означает терпимость к *обрезанному* `elapse` — и это надо обработать.**
Разница между дорогами существенна и в v1 не была названа:

- терпимый `LiveError` (хендлер вернул `Ok`) — `process_event` возвращает `ElapseResult::Ok`, цикл
  `elapse_` **продолжается**, остаток тика обрабатывается нормально;
- `BotError` из `recv_timeout` — `Err(error) => return Err(error)` [код `:462-464`], то есть
  **немедленный выход из `elapse_` посреди тика**.

Отсюда три обязательства у того, кто решит терпеть дорогу 1/3:

- **Тик неполон.** События, которые были бы прочитаны дальше, остались в shm-очереди
  (`subscriber_max_buffer_size = 10000` [код `ipc/config.rs:7`]) и приедут на следующем `elapse`.
  Не потеряны, но и не применены: значения `position()`, `orders()`, книги на этом тике — состояние
  «до обрыва», а не «на конец тика».
- **Батч-состояние обнулено.** Возврат по `Err` не проходит гейты §3.3 вовсе, поэтому обрезанный
  тик может отдать управление посреди чужого (и своего) батча — ровно тир, который §3 закрывает на
  штатных путях. То есть терпимость к дороге 1/3 **покупает риск (a) обратно**, и единственная защита
  здесь — гейт свежести из пункта (1).
- **Терпимость обязана быть ограниченной по частоте.** `elapse` при повторяющемся отказе возвращается
  **мгновенно** (ошибка приходит на первой же итерации), поэтому цикл стратегии, который просто
  `continue`-ит, превращается в busy-loop с торговой логикой на каждом обороте. Нужен счётчик/бэкофф
  с фатальным исходом при превышении — у `myhft` для этого есть готовая форма
  (`CircuitBreakerState`), см. §8.3 путь 4.

### 4.4 Отклонённые альтернативы

| Альтернатива | Цена / почему нет |
|---|---|
| **Имя коннектора в `LiveError.value`** (уже `Value::Map` на проводе) | Класс B и три отдельных минуса. (1) **512 байт.** HL кладёт в `value` строку, обрезанную до `MAX_ERROR_BYTES = 400` [код `hyperliquid/mod.rs:154,161-163`], и этот бюджет посчитан против сегодняшней формы. Нарушает fail-closed. |
| **Формат-строка `Custom(format!("{connector}: {msg}"))`** | Нулевая цена по API, но потребителю пришлось бы парсить прозу, чтобы решать про деньги. Это ровно та ошибка, которую §4.2 `AGENTS.md` уже оплатил на bybit: атрибуция должна быть структурным полем, а не текстом. |
| **Не слать heartbeat в market-data-only коннекторы** (лечить дорогу 3 в библиотеке) | Это политика: библиотека не знает, какой коннектор торговый, и узнать может только из нового поля конфигурации — то есть `myhft`-специфика в публичном API (§2 `AGENTS.md`). Плюс молчащий бот коннектор всё равно возьмёт под наблюдение только после первого heartbeat (§4.7 `AGENTS.md`), так что «не слать» меняет и семантику живости. Библиотека называет коннектор, решает потребитель. |

Классы по рубрике задачи: **A** — внутри форка; **B** — bincode-провод (`LiveEvent`/`LiveError`,

Добавлен **A′** — публичное API форка, слом только на этапе компиляции, без провода.

## 6. План тестов (MockChannel, mutation-grade)

База — `mod tests` в `live/bot.rs:798`: `MockChannel` [код `:812-852`] отдаёт заранее засеянную
очередь `(usize, LiveEvent)` и `Timeout` по опустошении; `QuietChannel` [код `:860-891`] молчит
всё отведённое время. Нужен один новый хелпер — `make_multi_connector_bot(&[(conn, symbol)], events)`
(сегодня `make_bot` жёстко зашивает `"mock"` [код `:921`]).

Все пины §6.1 переписаны под единообразный `any_open`; пин v1 №2
(`a_batch_defers_only_its_own_connectors_return`) **удалён**, потому что он фиксировал тир как
контракт: он требовал, чтобы чужой `Feed` возвращался немедленно при открытом батче HL.

### 6.1 Изоляция батчей — тир не должен быть возможен

1. `a_foreign_batch_end_cannot_release_a_batch_that_is_still_open` — инструменты `0 = ("hl","BTC")`,
   `1 = ("bnc","BTCUSDT")`. Скрипт: `(0, BatchStart)`, `(0, Feed{px 100, qty 0})` — снимает
   текущий лучший бид, `(1, BatchEnd)` — **чужой**, `(0, Feed{px 99, qty 5})`, `(0, BatchEnd)`.
   Наблюдаемое — money-shaped: на момент возврата `best_bid == 99.0`, а **не** пустая книга.
   Мутация: вернуть один глобальный `bool`/счётчик на весь бот → чужой `BatchEnd` снимает флаг →
   возврат на пустой книге → падает.
2. `an_open_batch_anywhere_defers_a_foreign_connectors_feed` — **пин на BLOCKER-1.** HL-батч открыт
   (`(0, BatchStart)`, `(0, Feed{px 100, qty 0})`), приходит `(1, Feed)` от Binance. `wait_next_feed`
   **не должен** вернуться: следующим в скрипте идёт `(0, Feed{px 99, qty 5})`, `(0, BatchEnd)`, и
   утверждение снова money-shaped — вернулись с `best_bid == 99.0`. Мутация: сделать гейт `:431`
   per-connector (`!batch_open[conn_of_inst[inst_no]]`, вариант v1) → возврат на чужом `Feed` с
   пустой книгой → падает.
3. `a_return_happens_once_the_last_batch_closes` — парный к №2 пин на **живость**, иначе №2
   удовлетворяется реализацией «никогда не возвращаться». Оба батча открыты (`(0, BatchStart)`,
   `(1, BatchStart)`), приходит `(0, Feed)`; `(1, BatchEnd)` возврата **не** даёт; `(0, BatchEnd)` —
   даёт, и результат — `MarketFeed`… с поправкой на варт §10: на `BatchEnd`-пути возвращается
   `Ok(ElapseResult::Ok)`, и тест пинит **именно сегодняшнее** значение, чтобы варт не «починился»
   молча. Мутация: держать возврат безусловно → падает.
4. `a_pending_response_is_released_only_when_the_last_batch_closes` — отложен `OrderResponse` HL при
   открытом батче Binance; выпуск только когда закрылись оба. Мутация: `if wait_resp_received` без
   `&& !any_batch_open()` → падает.
5. `a_nested_batch_is_not_released_by_its_inner_batch_end` — **пин на §3.6**, один коннектор:
   `BatchStart`, `Feed{px 100, qty 0}`, `BatchStart` (регистрационный), `BatchEnd` (его же),
   `Feed{px 99, qty 5}`, `BatchEnd`. Возврат с `best_bid == 99.0`. Мутация: `Vec<u32>` → `Vec<bool>`
   → внутренний `BatchEnd` рвёт внешний батч → падает. Обоснование сценария — реальные call-site-ы
   коннектора [код `connector/src/main.rs:339-391` против `hyperliquid/public_stream.rs:652-658`].
6. `any_open_batch_defers_an_unrelated_symbols_return` — два HL-символа на **одном** коннекторе: батч
   одного задерживает возврат по другому. Пин на §3.6: остаток осознанный, и тест — исполняемая
   документация, чтобы его не «починили» случайно.
7. `an_orphaned_batch_start_cannot_hold_the_bot_past_its_hold_ceiling` — **P0, не P1.** Нужен
   `LoopingChannel` (события никогда не кончаются, батч открыт и не закрывается) + `bot.max_batch_hold
   = 20ms`; `elapse` обязан вернуться. Мутация: убрать потолок → тест висит (падает по таймауту
   харнесса). Второе утверждение того же теста: в логе `warn` названо имя застрявшего коннектора
   (иначе `open_connector_names()` — мёртвый код, а оператору нечего грепать).

### 6.2 Атрибуция происхождения — шов вместо разделяемой памяти

`IceoryxUnifiedChannel::recv_timeout` не юнит-тестируется: `IceoryxChannel::new` поднимает настоящие
iceoryx-сервисы [код `iceoryx.rs:221-230`]. Поэтому — тот же приём, что §4.2 `AGENTS.md` применил к
bybit (`serve(write, read)`), но **на две глубины**, потому что пинить надо два разных утверждения.

**(а) Чистая атрибуция события.**

```rust
fn attribute(ev: &LiveEvent, origin_inst_no: usize, map: &HashMap<String, usize>) -> Option<usize>
```

8. `attribute_marks_a_markerless_event_with_the_channels_origin` — безсимвольные варианты →
   `Some(origin_inst_no)`, символьные → `map.get(symbol)`, неизвестный символ → `None`. Мутация:
   вернуть `Some(0)` для безсимвольных → падает.

**(б) Привязка `origin_inst_no` к опрошенному каналу — MAJOR-6.** Пункт (а) сам по себе — зелёный пин
над недоказанным: он проверяет, что *переданный* origin доедет до результата, и ничего не говорит о
том, что переданный origin принадлежит тому каналу, который только что опросили. Это ровно та форма
провала, которую §4.2 `AGENTS.md` уже оплатил на bybit (атрибуция, которую можно было заменить
константой при 196/196 зелёных). Поэтому round-robin тоже выносится в шов:

```rust
trait PolledSource {                       // реализует IceoryxChannel; в тестах — FakeSource
    fn name(&self) -> &str;
    fn origin_inst_no(&self) -> usize;
    fn symbol_to_inst_no(&self) -> &HashMap<String, usize>;
    fn receive(&self) -> Result<Option<(u64, LiveEvent)>, ChannelError>;
}

fn poll_round_robin<C: PolledSource>(sources: &[C], ch_i: &mut usize, id: u64)
    -> Result<Option<(usize, LiveEvent)>, BotError>
```

`recv_timeout` остаётся часами и циклом вокруг этого шва; никакой iceoryx в тесте не поднимается.

9. `each_polled_channel_stamps_its_own_origin` — два `FakeSource` с **разными** `origin_inst_no`
   (например 0 и 7) и разными очередями, каждая начинается с `BatchStart`. Утверждения: первый вызов
   даёт `(0, BatchStart)`, второй — `(7, BatchStart)`, курсор идёт round-robin. Мутации, каждая своя:
   (i) брать `sources[0].origin_inst_no()` для всех → падает; (ii) константа `0` → падает (это ровно
   сегодняшний код); (iii) не двигать `ch_i` → падает.
10. `a_failed_receive_names_the_channel_it_polled` — `FakeSource`, отдающий `Err(ChannelError::…)`,
    стоит вторым; ошибка приходит как `BotError::Channel { connector: "bnc", .. }`. Мутация:
    `BotError::Custom` → падает.

### 6.3 Ошибка чужого коннектора не останавливает торговлю HL

11. `an_error_is_attributed_to_the_connector_it_came_from` — хендлер пишет `(connector, kind)` в
    `Rc<RefCell<Vec<_>>>`; `(origin_inst_no_of_bnc, LiveEvent::Error(..))` даёт `"bnc"`.
    Мутация: заменить `conn_of_inst[inst_no]` на `0` → получаем `"hl"` → падает.
12. `a_tolerated_market_data_fault_does_not_end_the_elapse` — **главный money-path пин.** Хендлер:
    `Ok(())` для `"bnc"`, `Err(BotError::Interrupted)` для `"hl"`. Скрипт:
    `(bnc, Error(ConnectionInterrupted))`, затем `(hl, Feed)`. Утверждения: `elapse` вернул `Ok`,
    HL-книга обновлена (события **после** чужой ошибки обработаны). Мутация: вернуть безымянный
    хендлер → фатально на первой ошибке → падает.
13. `a_fault_on_the_trading_connector_still_propagates` — тот же хендлер, ошибка от `"hl"` → `Err`.
    Пин на fail-closed-направление.
14. `a_channel_fault_names_the_connector_it_came_from` — `FaultyChannel` отдаёт
    `Err(BotError::Channel { connector: "bnc", .. })` из `recv_timeout`; проверяется, что `elapse`
    доносит имя до вызывающего (это то, на чём `myhft` строит терпимость), **и** что вызов
    оборвался — пин на §4.3(2): в скрипте после ошибки стоит `(hl, Feed{px 99})`, и книга HL после
    возврата его **не** содержит. Обрезание — часть контракта, а не сюрприз.
15. `a_failed_heartbeat_send_names_the_connector_it_could_not_reach` — **пин на дорогу 3.**
    `SendFailingChannel` возвращает `Err(BotError::Channel { connector: "bnc", .. })` для `inst_no`
    Binance и `Ok(())` для HL; `elapse` доносит имя. Мутация: `BotError::Custom(..)` в
    `IceoryxUnifiedChannel::send` → имени нет → падает.

### 6.4 Одно-коннекторная эквивалентность

16. `the_single_connector_gates_match_the_previous_implementation` — дифференциальный тест:
    30-строчная референс-модель старых гейтов (`batch_mode: bool`, `wait_resp_received: bool`)
    прогоняется на случайных скриптах событий (фиксированный seed, ~10k трасс) для **одного**
    коннектора и сравнивается по кортежу «возвращённый `ElapseResult` + число обработанных событий».
    Генератор выдаёт **сбалансированные невложенные** батчи — оба исключения из §3.5 намеренные, и
    подмешивать их сюда значило бы пинить старое поведение как эталон; они покрыты пинами 5 и 7.
17. Вся существующая пачка (`snapshot_*`, `position_observed`, heartbeat-тесты `:1102-1280`) остаётся
    зелёной без правок — это регрессионная сетка на неизменность одно-коннекторного пути.

## 8. `myhft`: парный апгрейд, и почему §8 v1 был неверен

### 8.3 Точные изменения, по одному на путь

Цель, сформулированная как инвариант: **отказ market-data-only коннектора не может привести к выходу
процесса, а отказ торгового — обязан, ровно как сегодня.**

Опорная структура (в `myhft`, не в форке): роль коннектора.

```rust
// myhft: конфиг бота знает, кто из коннекторов торговый. Форк об этом не знает и не должен.
enum ConnectorRole { Trading, MarketDataOnly }
fn role_of(connector: &str) -> ConnectorRole   // из конфига, дефолт — Trading (fail closed)
```

Дефолт **`Trading`** намеренно: незнакомое имя должно оставаться фатальным, иначе опечатка в конфиге
молча делает торговый коннектор терпимым.

1. **Путь 1 — `handle_live_error` принимает происхождение.**
   `pub fn handle_live_error(role: ConnectorRole, live_error: LiveError) -> Result<(), BotError>`
   [код-bot `lib.rs:282`]: ветка `ConnectionInterrupted` [код-bot `lib.rs:284-287`] возвращает
   `Err(BotError::Interrupted)` **только** при `Trading`; при `MarketDataOnly` — `warn!` + `Ok(())`.
   Четыре существующих юнит-теста [код-bot `lib.rs:1123-1149`] обновляются и **удваиваются**: каждый
   kind × каждая роль. Отдельный пин на то, что `MarketDataOnly` + `ConnectionInterrupted` не даёт
   `Err` — это и есть исправляемый баг.
2. **Путь 2 — счётчик criticals per-connector.** Одно `CircuitBreakerState` на коннектор
   (map `connector → CircuitBreakerState`, строится там же, где сегодня одно [код-bot `main.rs:309`]).
   `record_critical` [код-bot `main.rs:107-110`] пишет в состояние **источника**. Проверка раз в тик
   [код-bot `lib.rs:576-584`] остаётся выходом **только** для торгового коннектора; шторм criticals
   market-data-коннектора не выходит из процесса, а помечает сигнальную книгу негодной (политика #20,
   не форка) — и обязательно логируется своим событием, чтобы «терпимо» не значило «незаметно».
3. **Путь 3 — классификатор per-connector.** `select_classifier` [код-bot `main.rs:218`] вызывается
   для **каждого** зарегистрированного коннектора; хендлер выбирает по `origin`. Правило
   fail-closed сохраняется в обе стороны: **торговый** коннектор без классификатора → `exit(2)`, как
   сегодня; **market-data-only** без классификатора → `RateLimitKind::None` и никаких `record_*`
   (у Binance-md классификатора нет и не нужен — рейт-лимит на чтении публичного стрима нас не
   останавливает). Без этой правки HL-классификатор разбирал бы Binance-payload и мог бы защёлкнуть
   `hard_flag`, из которого нет выхода, кроме рестарта [код-bot `circuit_breaker.rs:140-142`].
4. **Путь 4 — ветка `Err(err)` разбирает `BotError::Channel`.** [код-bot `lib.rs:429-435`]:

   ```rust
   Err(BotError::Channel { connector, message })
       if matches!(role_of(&connector), ConnectorRole::MarketDataOnly) => {
           // §4.3(2): тик обрезан, батч-состояние сброшено, повтор возможен каждый тик.
           transport_faults.record(connector, now);          // ограниченная терпимость
           if transport_faults.is_storm(now) { return Err(1); }
           warn!(event = "market_data_channel_fault", %connector, %message);
           continue;
       }
   Err(err) => { error!(event = "live_loop_error", ?err); return Err(1); }
   ```

   Три обязательства из §4.3(2) должны быть выполнены **здесь**, иначе терпимость хуже падения:
   (i) счётчик/бэкофф — обязателен, потому что обрезанный `elapse` возвращается мгновенно и `continue`
   без ограничения даёт busy-loop с торговой логикой на каждом обороте; (ii) сигнальная книга должна
   быть под stale-гейтом (пункт 5 ниже) — обрезанный тик не гарантирует полноты; (iii) heartbeat в
   этот коннектор не доехал, значит он сметёт ордера этого бота у себя — на market-data-only это
   безвредный no-op (ордеров там нет), и это ещё одна причина, почему терпеть можно **только**
   market-data-only.
   Поскольку `gridtrading` генерик по `I: Bot<MD>`, предикат роли передаётся замыканием из `main`,
   где конкретные имена известны; нового API в форке для этого не нужно.
5. **Путь 5 — stale-гейт на сигнальную книгу.** [код-bot `lib.rs:477-514`] сегодня читает
   `feed_latency(0)`. Добавить asset 1 со **своим** порогом и **своим** исходом: замершая сигнальная
   книга не выходит из процесса, а выключает сигнал (бот возвращается к режиму без сигнала — политика
   #20). Это обязательное условие пунктов 1 и 4: без него терпимость покупает тихий неверный сигнал.
6. **Путь 6 — `snapshot_ready` второго коннектора.** [код-bot `lib.rs:441-460`] гейтит **старт
   торговли** по `snapshot_ready(0)`. Расширять этот гейт на asset 1 **не следует**: тогда недоступный
   Binance блокировал бы старт торговли на HL — та же болезнь с другой стороны. Правильный ответ:
   готовность сигнальной книги гейтит **сигнал**, а не торговлю, и её отсутствие после разумного
   окна — это лог + работа без сигнала.
7. **Замечание по heartbeat (из v1, остаётся верным).** Бот шлёт `Heartbeat` на **каждый** `inst_no`
   [код `bot.rs:363-366`], то есть и в market-data-only коннектор. Тот возьмёт бота под наблюдение и
   при его смерти «сметёт» ордера, которых там нет — безвредный no-op, но в логах он будет виден, и
   оператора об этом надо предупредить заранее.

### 8.4 Развилка веток `myhft`, которую нельзя не заметить при мердже

Основное дерево и деплой-ветки **разошлись именно в том месте, которое правит §8.3 пункт 1**. В
worktree `~/myhft-signal` (`feat/signal-openpermit` @ `e32e6fd`, там живёт #20 step 3)
`ConnectionInterrupted` **уже не фатален**: хендлер возвращает `Ok(())`
[код-bot-signal `lib.rs:309-322`], `build_error_handler` защёлкивает грань через
`state.mark_interrupted()` [код-bot-signal `main.rs:184-186`], а цикл раз в тик читает
`take_interrupted()` и **снимает котировки** на ограниченное окно, дедлайн которого — тот же
stale-feed guard [код-bot-signal `lib.rs:682-722`].

Что это меняет для нашего дизайна: **вред меняет форму, но не исчезает**. На той ветке реконнект
Binance не убьёт процесс — он **снимет сетку HL** и отправит бота в «recovering», который ждёт
свежий кадр по **asset 0** [код-bot-signal `lib.rs:694-703`]. То есть market-data-only отказ
по-прежнему останавливает торговлю, просто тихо. Правка та же самая и та же по смыслу: `mark_interrupted`
должен вызываться **только** для торгового коннектора, а роль берётся из origin. Пункты 2–6 §8.3
применяются к обеим веткам без изменений.

Практический вывод для планирования: пин-бамп форка и правка `myhft` должны делаться **на той ветке,
куда поедет step 4**, а не на основном дереве, и обе редакции `handle_live_error` надо привести к
origin-aware виду при мердже. Все три прочитанных дерева (`myhft`, `myhft-integration`, `myhft-signal`)
пинят один и тот же rev форка `cf35fd5`, так что расхождение чисто в коде бота.

## 9. Открытые вопросы

1. **Значение `MAX_BATCH_HOLD` не выведено из измерения.** Нужно время дренажа самого большого
   реального батча: 200-уровневый снапшот Binance ≈ 400 отдельных iceoryx-сообщений, и на каждое
   `recv_timeout` делает `node.wait(Duration::from_nanos(1))` [код `iceoryx.rs:335`] — стоимость
   этого вызова в репозитории не измерена, бенчмарков нет. Потолок должен быть на порядки выше
   дренажа и заметно ниже 10-секундного окна живости коннектора и 5-секундного stale-гейта бота.
   До измерения — **[?]**. Мерить до **live** второго коннектора (P1); в тестнете P0 едет с
   заведомо консервативным значением.
2. Потолок — `const` или builder-опция? `const` держит политику вне библиотеки, опция даёт
   оператору ручку. Склоняемся к `const` + приватное поле для тестов; пересмотреть, если появится
   бэкенд с легитимно длинными батчами.
3. **Реально ли теряется `BatchEnd`?** `subscriber_max_buffer_size = 10000` [код `ipc/config.rs:7`,
   применяется в `iceoryx.rs:87,98,128,139`]; что делает iceoryx2 0.6.1 при переполнении (перезапись
   старейшего vs блокировка) — **[?]**, не проверено. Ответ определяет, теоретическая §3.4 нужда или
   практическая; на приоритет он **не влияет** — потолок в P0 нужен из-за §3.4 («изоляция без потолка
   хуже сегодняшнего») независимо от частоты потерь. Проверять по исходникам iceoryx2, не по
   документации.
4. **Fairness round-robin при N коннекторах.** Ордерные ответы торгового коннектора чередуются 1:1
   с потоком маркет-даты чужого, и при единообразном `any_open` (§3.3) чужой батч ещё и задерживает
   их доставку стратегии. Приоритет торгового канала — возможное улучшение латентности, но
   ордерные ответы HL едут по **тому же** каналу, что и его маркет-дата, так что приоритет внутри
   канала этим не решается. Не измерено, из P0 исключено. Метрика, которую стоит снять на step 4:
   распределение задержки возврата `elapse` при открытом чужом батче.
5. Когда понадобится **per-instrument** изоляция (HL с 16 монетами на одном коннекторе), путь —
   символ в маркере батча, класс B, и это **не** append-only (§3.7). Триггер: измеренная задержка
   возврата по монете A из-за кадров монеты B, превышающая требования перекотировки. Пока не
   наблюдалось.
6. `&str` или типизированный `ConnectorId(usize)` в `ErrorHandler`? Взято `&str`: это то, что
   оператор грепает, и `myhft` уже логирует `classifier = %connector_name` [код-bot `main.rs:86,96`].
7. **Upstream-абилити смены подписи `ErrorHandler`.** Апстрим может предпочесть аддитивный вариант.

   форке держать строгий. Решать при подготовке PR, не сейчас.
8. **Вложенность батчей внутри коннектора — вывод, а не измерение.** §3.6 показывает её из двух
   call-site-ов коннектора; ни разу не наблюдалась в логе, потому что наблюдать нечем (маркеры

## 10. Чего этот дизайн НЕ делает

- **Не делает батчи атомарными по-настоящему.** `Err(BotError::Timeout)`-выход [код `:443-458`]
  возвращает управление посреди батча и сегодня, и после правки; батч-состояние сбрасывается на
  входе в каждый `elapse_`, поэтому батч, переехавший границу вызова, не защищён (§3.7, последняя
  строка). Сюда же — возврат по `Err` из дороги 1/3 (§4.3(2)). Обещание остаётся «стратегия не увидит
  промежуточное состояние, **пока события идут и пока никто не отказал**».
- **Не меняет `BatchEnd → Ok(ElapseResult::Ok)`** [код `:417`] на возврат отложенного
  `MarketFeed`/`OrderResponse`. Это wart: вызывающий `wait_next_feed` получает `Ok` там, где кадр
  фактически пришёл. Сохранён намеренно ради §3.5 и **запинен** тестом 3, чтобы не «починился» молча;
  `myhft` сегодня не затронут (использует `elapse` и матчит `Ok(ElapseResult::Ok)`
  [код-bot `lib.rs:419-420`]). Починка — отдельное решение с собственным пином.
- **Не трогает `BotError::Interrupted` от `node.wait`** [код `iceoryx.rs:365-367`]: отказ общий на
  node, а не на коннектор, и остаётся фатальным (путь 7 в §8.1).
- **Не даёт per-instrument изоляции** (§3.6) и не касается leader-book gap-repair — сигнальная
  книга и её починка после разрыва живут в отдельном item #20.
- **Не различает вложенный батч и потерянный маркер** (§3.6): на проводе они одинаковы. Лишний
  `BatchEnd` пропадает в `saturating_sub`, лишний `BatchStart` ловится только потолком §3.4.
- **Не лечит §4.1 `AGENTS.md`**: `LiveBot` по-прежнему игнорирует `DEPTH_SNAPSHOT_EVENT` и
  `DEPTH_BBO_EVENT`, поэтому регистрационный depth-снапшот в стакан бота не попадает и на втором
  коннекторе тоже: `orderbook_depths` (или его аналог у venue) обязан содержать инкрементальный
  стрим.
- **Не добавляет политику в библиотеку.** Что фатально, а что терпимо, решает `error_handler` и цикл
  потребителя — §1.1. Библиотека добавляет только *факт* происхождения; §8.3 — это работа в `myhft`,
  а не в форке.

## 11. Что поехало в P0 (2026-08-05) и чем это отличается от v2

Реализовано целиком §3.1–3.4 и §4.1–4.2 плюс правки §5 строк 4–6. Провод не тронут: `git diff`
по `hftbacktest/src/types.rs`, `live/ipc/config.rs` и всему `connector/` пуст. Подпись `Channel`
не менялась. `myhft` не трогался — его миграция (§8.3) отдельная задача.

Коммиты: `c896f26` (швы приёмника), `f63abae` (изоляция батчей + проверка границ), `3f0ba8a`
(пины потолка), `073d836` (происхождение ошибки + фан-аут heartbeat).

### 11.1 Три расхождения с текстом v2, все осознанные

1. **Потолок — это hold-clock и gate-release, а не ранний возврат из §3.4.** Набросок §3.4
   вставляет проверку внутрь гейта по длительности, и этого **недостаточно**: путь, который
   потолок обязан ограничить, — `wait_order_response` (60 с, зашитых в `submit_order`/`cancel`).
   Ответ на ордер, уже полученный и отложенный за незакрытым батчем, выпускается только тогда,
   когда батч перестаёт *держать*. Поэтому у каждого коннектора есть `BatchHold { depth, since }`,
   а `batch_holds(elapsed)` — «открыт **и** не старше потолка». Пин
   `a_wait_order_response_is_released_at_the_hold_ceiling` краснеет ровно на варианте
   «выпускать отложенное только по настоящему `BatchEnd`», остальные при этом зелёные.
2. **`BatchEnd` больше не возвращает из своей ветки.** Освобождение отложенного результата —
   одна проверка `wait_resp_received && !holds` в конце итерации; `BatchEnd` доходит до неё сам.
   Это же место — точка выпуска по потолку. Для сбалансированных трасс поведение
   бит-в-бит прежнее, и это не обещание, а дифференциальный тест §6.4.
3. **Проверка границ стоит в двух местах**, а не в одном, как в §3.1: в начале `process_event`
   (чтобы `get_unchecked_mut` там доказывались локально) и в `connector_of` — потому что
   батч-ветки `elapse_` лезут в `conn_of_inst[inst_no]` **раньше**, чем вызывается
   `process_event`. Прогон пина против старого кода не «падал», а **абортил процесс** на UB-чеке
   `slice::get_unchecked_mut` — это и был red.

### 11.2 Чего в v2 не было вовсе

- **Фан-аут heartbeat (§2.2 дорога 3, вторая половина).** `heartbeat` слал в каждый инструмент с
  `?` внутри цикла и ставил `last_heartbeat` только после него: недостижимый коннектор голодил
  всех, кто за ним, **навсегда** — повтор начинался с того же падающего индекса. Коннектор,
  переставший слышать бота, сметает его ордера, то есть market-data-only венью мог снести сетку на
  торговой. Теперь: сказать всем, вернуть первую ошибку после цикла, `last_heartbeat` двигать в
  любом случае (иначе терпимый потребитель получает ошибку на **каждом** `elapse`, а не раз в
  интервал). Пины `a_failed_heartbeat_send_names_the_connector_it_could_not_reach` и
  `a_heartbeat_that_could_not_be_delivered_does_not_retry_before_its_interval`.
- **`SymbolRegistry`** — `symbol_to_inst_no` + `origin_inst_no` вынесены из `IceoryxChannel`,
  потому что тот не конструируется в тесте (поднимает сервисы iceoryx), а «представитель — самый
  младший зарегистрированный» надо пинить.
- **Borrowck в `Error`-ветке:** хендлер берётся через `as_ref()`, а не `as_mut()`. `ErrorHandler`
  — это `Fn`, поэтому имя коннектора и хендлер держатся двумя *общими* заимствованиями `self`;
  с `as_mut()` это не компилируется.
- **Одно чтение часов на итерацию,** взятое до обработки события, а не после (раньше — после, в
  конце тела цикла). Гейты, потолок и heartbeat спрашивают про один и тот же момент.

### 11.3 Значения и остатки

- `MAX_BATCH_HOLD = 250 ms`, приватное поле, тесты его укорачивают. **Открытый вопрос §9.1 остаётся
  открытым:** дренаж самого большого реального батча не измерен. Сверху потолок ограничен жёстко
  (10-секундное окно живости коннектора, 5-секундный stale-гейт бота), снизу — нет.
- **Call-site `warn!` не запинен.** Запинены `stuck_connectors` (арифметика потолка и имя, на
  часах, которыми управляет тест) и само поведение выпуска. Перехват `tracing` в тестах этого
  репозитория гоняется (`AGENTS.md` §4.2: 3 падения на 60 прогонов на пине ровно такой формы), а
  флакующий money-path-набор дороже этого пина.
- Остатки §10 не изменились: `Timeout`-выход по-прежнему возвращает управление посреди батча,
  батч-состояние по-прежнему живёт внутри одного вызова, `BatchEnd → Ok(ElapseResult::Ok)`
  сохранён (и запинен), per-instrument изоляции нет.
