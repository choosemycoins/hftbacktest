## 0. Решения

1. **Провод не меняется.** Запрос — `LiveRequest::Order` с `req = Replaced` (7). Отказ —
   `LiveEvent::Order` с `req = Rejected` (6), `status = None`, `exch_timestamp = 0` (§2). Оба
   значения — в enum с апстрима; новых вариантов нет, §2 `AGENTS.md` не задет.
2. **`Connector::modify` — метод трейта с телом по умолчанию = отказ** (fail closed).
   bybit, binancefutures, binancespot, lighter — ноль строк.
3. **Бот: правка — opt-in.** `LiveBotBuilder::native_modify(bool)`, по умолчанию `false` →
   `modify` = `Err(Unsupported)` до любой отправки (поведение шага 1). Включать, только когда
   **все** коннекторы бота правку реализуют (сегодня — HL ≥ C7); ≥ C3 — лишь совместимость (§6).
   Отказ правки — штатный ответ, не фатален: стратегия откатывается на cancel+new (§3.5; §14 Р4).
   Гейт потребителя по возрасту `req == Replaced` — в любом случае.
4. **Пока правка в полёте,** `orders()` показывает то, что стоит на бирже, плюс `req = Replaced`.
   Ack приносит новые значения; отказ снимает только `req`.
5. **В полёте всё прочее по ордеру запрещено локально** (вторая правка, отмена) — как в
   бэктесте (`OrderRequestInProcess`): в боте — `InvalidOrderStatus`; в коннекторе, если бот
   полёта не видел (§3.3, две последние строки), — отказ с `OrderError`: правке — T26, отмене — T70.
6. **HL: только `batchModify`, по одному на запрос.** Ack одиночного `modify` — без oid [F2];
   стоят одинаково [F1].
7. **HL: цель правки — cloid, cloid сохраняется; oid монотонен.** Ключ ордера в коннекторе —
   cloid; `oid` — текущий venue-id; запись с oid меньше текущего — устаревшая [F9, P3].
   Списка `retired` нет. Следствие: cloid не называет **запрос**. Ответ `/exchange` и таймер
   действуют на правку только по её `id` (счётчик коннектора), сверка — только после её
   `resolve_after`; ответ submit или отмены — только на свой маркер `req` (§5.2 «Идентичность
   запроса»).
8. **HL: каждый `batchModify` несёт `expiresAfter = t_подписи + EXCHANGE_TIMEOUT` (10 с).**
   Неопределённость (сбой транспорта или ответ без явного вердикта, §5.4) разрешается
   **не раньше `expiresAfter + SETTLE`**:
   правка, не исполненная к `expiresAfter`, не исполнится никогда [P1 → Q12, P2], и список
   открытых ордеров — окончательный ответ (§5.5).
9. **Ответ на каждый `Replaced` — ровно один, на штатном пути не позже B от подписи** (HL 20 с,
   §5.6). Дальше — сбой: гейт потребителя (B + 5 с от отправки ботом) выводит бота (§6).
10. **Бюджет:** перекотировка — 1 запрос вместо 2; `batchModify` из n — n [F1; перемерить Q11].
11. **Вне scope MON-4:** Python live-modify (§3.6); поздняя постановка `order` после сбоя
    транспорта (тот же класс, §5.5); гонка свипа с ордером в полёте (§5.8).

## 2. Провод

| | `order_id` | `req` | `status` | цена/объём | `exec_*` | `exch_timestamp` | `local_timestamp` |
|---|---|---|---|---|---|---|---|
| запрос (бот → коннектор) | тот же | `Replaced` | копии бота | **новые**, `leaves_qty = qty` | 0 | копии бота | время отправки — ключ корреляции |
| ack (коннектор → бот) | тот же | `None` | `New` | принятые биржей (после нормализации) | 0 | max копии коннектора | не читается |
| отказ (коннектор → бот) | тот же | `Rejected` | **`None`** | не читаются | 0 | **0** | **эхо запроса** |

- Ack: `status = New` (замена — свежий ордер; бэктест так же, `ack_modify`), `exch_timestamp`
  не откатывается — иначе сторож `live/bot.rs:568` отбросит ack и ордер останется в
  `Replaced` навсегда. Пины: бот — T17; коннектор — T41 (штамп ack ≥ последнего опубликованного
  по ордеру; T17 строит ack сам и мутацию коннектора не видит).
- **Порядок публикации = порядок переходов** (T65) — обратная сторона T17. Ack несёт
  `exch_timestamp` = max копии, и сторож `>=` равный штамп пропускает. Сегодня копия уходит в
  `ev_tx` уже после замка `OrderManager` (`private_stream.rs:463-469, 491-501`), а публикуют и
  поток, и задачи ордеров. Снимок потока, снятый до ack, может уйти после него: бот снова видит
  старую цену и `Replaced`, новый уровень выглядит пустым, хотя ордер на нём стоит, — до
  следующего события по ордеру или гейта (§6). После отказа (`exch_timestamp = 0` сторож не
  двигает) — то же. Поэтому переход и отправка копии — под одним замком (unbounded-канал не
  блокирует): один помощник, через него — все переходы, публикующие копию.
- Отказ: `status = None` и `exch_timestamp = 0` — **всегда**, и в `publish_modify_rejection`,
  и в HL (T9, T33). Зачем: (а) новый бот проводит отказ по ветке §3.2 мимо сторожа, а старый
  бот без ветки сторожем отбрасывает его для любого ордера с ack; (б) `last_order_latency` не
  портится (T57); (в) чужой отказ (`Order` идут `TO_ALL`, `main.rs:397`) старый бот вставит
  как **неактивный** фантом (`active()` = false, `clear_inactive_orders` его снимет), а не как
  живой `New` по цене, которой на бирже не было. Совпадение `order_id` двух ботов на символе —
  тот же класс, что сегодня с любым чужим `Order`; вне scope.
- Сразу за отказом — `LiveEvent::Error(OrderError, Value::String ≤ 400 байт)`. Порядок «ордер,
  потом ошибка» — как `expire_and_report`: состояние бота чисто до `error_handler` (T9).
- `req = Rejected` сегодня не публикует ни один коннектор (grep по `connector/src`) — маркер
  однозначен. `status = Rejected` (venue-статус «rejected» у HL) — другое поле.
- В `Order` строк нет (только короткий `symbol` рядом), текст режет `clamp_message` — потолок
  512 байт (MON-8) не задет (T10).

## 3. Бот (`hftbacktest/src/live/bot.rs`)

### 3.1 `LiveBot::modify` (сейчас `todo!()`, `:1034-1043`)

```text
modify(asset_no, order_id, price, qty, wait):
  !self.native_modify   → Unsupported                     // первым, до любой отправки: T58
  instrument            → InstrumentNotFound              // T15
  order                 → OrderNotFound                   // T15
  !order.cancellable()  → InvalidOrderStatus              // active && req == None: T13, T14
  now = Utc::now()
  request = order.clone(); price_tick = round(price / tick); qty = leaves_qty = qty;
            exec_qty = 0; exec_price_tick = 0; req = Replaced; local_timestamp = now   // T11
  channel.send(Order{symbol, request})?                   // ошибка → копия НЕ тронута: T16
  order.req = Replaced; order.local_timestamp = now       // метка — только после send: T12, T16
  wait → wait_order_response(asset_no, order_id, <параметр MON-11>)                     // T18, T19
```

- `native_modify`: поле `LiveBot`, `LiveBotBuilder::native_modify(bool)`, умолчание `false`.
  Док метода — по образцу `heartbeat_interval`: старый коннектор `Replaced` не понимает и не
  ответит никогда (§6). Тест шага 1 (`live_modify_returns_unsupported_error_instead_of_panicking`)
  остаётся пином умолчания.
- Метка после `send`, в отличие от `submit_order`/`cancel` (те метят до): неотправленный запрос
  не должен держать ордер в `Replaced` (T16).
- `round`, как `submit_order` и `Local::modify` (T11 берёт цену не на тике).
- `qty` = сколько ордер простоит после правки (новый `leaves_qty`), как `Local::modify`
  (`proc/local.rs:194-231`, пин `amending_the_price_rests_the_amended_quantity`). Частичный филл
  до правки + правка на q → экспозиция f + q; в бэктесте так же; на HL — допущение A1.
- Локальных проверок цены/объёма нет: нормализация и отказ — в коннекторе (§5.7).

### 3.2 Ответ: ветка `req == Rejected` в `process_event`

Первой в `LiveEvent::Order`: до записи `last_order_latency` (`:557`), до хука и сторожа
`exch_timestamp` (`:563-578`) общего пути.

```text
LiveEvent::Order{order}:
  received_order_resp — как сейчас (по order_id)                              // T6
  if order.req == Rejected:                                                   // T5
      if order.exch_timestamp > 0 { last_order_latency = … }                  // у отказа 0: T57
      match orders.get_mut(order.order_id):
        Some(ex): hook(ex, &order)?                                           // T55
                  if ex.req != None && ex.local_timestamp == order.local_timestamp:   // T2
                      if ex.req == New { ex.status = Expired }                // паритет с Local: T4
                      ex.req = None                          // статус/цена/объём не трогать: T1, T56
        None: ничего                                                          // НЕ вставлять: T3
  else: прежний путь (latency, hook, сторож, update()/insert)                 // T5, T17
```

- Мимо сторожа: отказ несёт `exch_timestamp = 0`, а копия бота к его приходу могла уйти
  вперёд по филлу; сторож `>=` (`:568`) съел бы отказ, ордер остался бы в `Replaced` (T7).
- `last_order_latency` — правило `Local` (`proc/local.rs:92`: только при `exch_timestamp > 0`);
  иначе `order_latency()` вернул бы `(t_mod, 0, now)` (T57).
- Финальный ордер (`Filled` с `req = Replaced` — филл старого ордера обогнал отказ) остаётся
  финальным: ветка меняет только `req` (T56).
- Сравнение `local_timestamp`: отказ на старый запрос не снимает флаг свежего (T2).
  `Order::update()` метку не копирует (`types.rs:632-634`) — у бота она = время последнего
  запроса.
- Это правило `Local::process_recv_order_` (`proc/local.rs:119-132`) плюс хук, как у прочих
  событий. Ветка `New → Expired` живым коннекторам не нужна (отказ submit-а они шлют как
  `Expired`) — она ради одного правила в обеих реализациях (T4).
- Та же ветка принимает локальный отказ **отмены** коннектором, пока правка в полёте (§5.7, Р3):
  `ex.req = Canceled` → `None`, как отказ отмены в `Local` (T70).

- Предпоследняя строка — свойство асинхронного протокола, а не порядка публикации (§2 его

  ответа первой правки (≤ B); он приходит своим чередом. `req` меткой не защищаем (решение лида,
  §14 Р2): семантика `Order::update` апстримная, а цена безопасна — стратегия повторяет или
  откатывается на cancel+new.

### 3.4 `wait`

`wait_order_response` возвращается на **первом** `Order`-событии этого id — им может оказаться
филл старого ордера (`req` ещё `Replaced`). Контракт как у submit/cancel: после возврата
смотреть `req` (T18).

### 3.5 Документ трейта `Bot::modify` (`types.rs:956-970`) — дописать

Предусловие (активен, запроса в полёте нет); `qty` — новый остаток (на HL — A1); пока
`req != None`, цена/объём **зависят от реализации** (live — подтверждённые биржей, бэктест —
запрошенные), стратегия их не читает; отказ оставляет ордер как был, но на HL может
сопровождаться его гибелью [Q10, Q13]; **GTX-правка, которая пересекла бы спред: в бэктесте
ордер умирает (`Expired`, T59), на HL — по итогам Q13** — после отказа стратегия смотрит
`status`, а не предполагает; в live правка выключена по умолчанию (`native_modify`) и тогда
отвечает `Err(Unsupported)`; на HL правка = 1 запрос бюджета. **Отказ правки — штатный ответ, а

## 4. Коннектор: маршрут и отказ по умолчанию

- `run_receive_task` (`connector/src/main.rs:189-204`): `Status::Replaced → connector.modify`.
  Матч выносится в чистую `route_order_request(Status) -> OrderRoute {Submit, Cancel, Modify,
  Invalid}` в `connector.rs`: `main.rs` без тестов, а маршрут — это и есть фича (T8).
- Трейт:

```rust
/// Amends price and size of a resting order. Must not block; answer through `tx`
/// exactly once: an acknowledgement (`req = None`) or a refusal (`req = Rejected`,
/// `status = None`, `exch_timestamp = 0`, `local_timestamp` echoed). The default
/// refuses — a backend without it fails closed.
fn modify(&self, symbol: String, order: Order, tx: UnboundedSender<PublishEvent>) {
    warn!(%symbol, order_id = order.order_id, "This backend does not support modify.");
    publish_modify_rejection(&tx, &symbol, order, "modify is not supported by this connector");
}
```

- `publish_modify_rejection` — свободная функция в `connector.rs`: `req = Rejected`,
  `status = None`, `exch_timestamp = 0`, `exec_* = 0`, `local_timestamp` не трогать; `Order`,
  затем `Error(OrderError)` (T9, T10). HL ею же отвечает на свои отказы — и на локальный отказ
  отмены, пока правка в полёте (§5.7, T70).
- **Почему не `Expired`** (как `reject_order`, `hyperliquid/mod.rs:738`): отвергнутая правка не
  снимает ордер, он стоит по старой цене. `Expired` → бот считает уровень пустым и котирует
  поверх живого ордера — двойная экспозиция (T9, T45).

## 5. Hyperliquid

### 5.1 Действие

`{"type":"batchModify","modifies":[{"oid": <cloid>, "order": <OrderWire>}]}`; в теле запроса —
`"expiresAfter": t_подписи_мс + 10 000`. Порядок ключей — протокол: `type, modifies`;
`oid, order`; `a, b, p, s, r, t, c`. `oid` полиморфен — `#[serde(untagged)] enum OidOrCloid
{ Oid(u64), Cloid(String) }`; шлём cloid. `t` — tif исходного ордера из копии коннектора
(`Alo` остаётся `Alo`), `r: false`, `c` = тот же cloid. Цена/объём — `normalize_price(side)` /
`normalize_size`, как в `new_order` (к пассиву) (T21, T25).

- **`expiresAfter`.** Одно значение — и в прообразе подписи, и в JSON-теле (T49). Прообраз —
  HL-нота §5.7: `keccak(msgpack ‖ nonce:u64be ‖ 0x00 ‖ 0x00 ‖ expires_after:u64be)`, хвост
  `0x00 ‖ u64be` — после байта «без vault». Сегодня `connection_id` (`signing.rs:112`) хвоста не
  знает: параметр `Option<u64>`, при `None` байты прежние (существующие golden не трогаются).
  Расхождение тела и прообраза даёт то же безликое «User or API Wallet … does not exist»,
  поэтому golden — **только из официального SDK**: `--golden` пробника выдаёт векторы
  `*_expires` (`sign_l1_action(…, expires_after, …)`, сверка с `action_hash` SDK) — вход T50.
  Прогнано 06.10 офлайн (SDK 0.24.0, без сети): прообраз пробника совпал с `action_hash` SDK на
  4 векторах из 4, с хвостом и без; векторы без `expiresAfter` байт-в-байт прежние. Пример —
  `batch_modify_by_cloid`, nonce 1700000000002, `expiresAfter` 1700000010002: `connection_id`
  `c0238950d8eb71be8b3ebfd042f5bff0ebbde9e5ec134c53bba28681391ee539`.
- Значение = `t_подписи + EXCHANGE_TIMEOUT` (`exchange.rs:370`): ответ, не пришедший за
  таймаут клиента, после `expiresAfter` исполненной правкой уже не станет [P1]. Часы —
  `SystemTime`, как у nonce.
- `batchModify`, не `modify`: стоят одинаково [F1], но только `batchModify` даёт статус на ордер и
  новый oid [F2, F3]. Форма отказа одиночного `modify` не измерена [Q7].
- Цель — cloid: oid после правки меняется [F4]; по cloid биржа находит живой ордер [F6, F7];
  по устаревшему oid — отказ [Q7]. Перепроверяется [Q3, Q9].
- Склейка нескольких запросов бота в один `batchModify` — не в v1 (§11.8).

### 5.2 Состояние в `OrderManager`

К `OrderExt` добавляется:

```text
modify: Option<PendingModify>   // не больше одной на ордер
PendingModify { id: u64, from_oid: u64, request_ts: i64, price: f64, size: f64,
                expires_at_ms: u64, resolve_after: Instant,
                held: Option<OrderUpdate>, phase: InFlight | Ambiguous }
```

`retired` нет: заменённый oid отличается от замены сравнением [P3]. `from_oid` — не `Option`:
правка ордера с ещё неизвестным oid отказывается локально (§5.7, T27).
- `id` — номер из счётчика `OrderManager` (`u64`, монотонен, в процессе не повторяется). Задача
  правки несёт `(cloid, id)` от подписи до разрешения. `request_ts` — только эхо в отказе (§2):
  он от бота и уникален лишь по допущению о чужих часах (§11.14).
- `resolve_after` — монотонные часы в момент подписи + EXCHANGE_TIMEOUT + SETTLE. Раньше этого
  момента список открытых ордеров о правке ничего не решает (§5.5). `expires_at_ms` — срок для
  провода (`SystemTime`, подпись + EXCHANGE_TIMEOUT, §5.1).

Инварианты, пока `modify.is_some()`:
- `settled_at = None` — сверка ордер не судит (тот же механизм, что для submit в полёте, §11.6
  HL-ноты) (T37);
- копия держит `req = Replaced`, и **ни одно событие его не снимает**. Сегодня
  `apply_order_update` пишет `req = None` безусловно (`ordermanager.rs:407`) — меняется: снимать,
  только когда правки в полёте нет (T36).

**Идентичность запроса.** cloid сохраняется (§0.7), и по нему не понять, на **какой** запрос
пришёл ответ. Штатный путь, без единого сбоя: поток закрывает правку #1 раньше HTTP (§5.3 c),
бот получает ack и сразу шлёт #2 от O2. При корреляции по cloid поздний HTTP #1
`[Resting{oid: O2}]` при `modify = #2` прошёл бы строкой «на месте» (O2 = `from_oid` #2): ack #2
до её исполнения, `modify = None`. Затем `canceled O2` идёт по b2 как терминал (ордер из карты,
боту `Canceled`), `open O3` — в «does not track»: сирота и двойная экспозиция. Поэтому каждый
асинхронный писатель пишет только по своему запросу:

| Писатель | Пишет только | Пин |
|---|---|---|
| ответ `/exchange` на правку, `settle_modify(cloid, id, answer)` | при `modify.id == id`; иначе ничего (лог — §5.4) | T46, T60 |
| задача правки после `resolve_after` (§5.5) | при `modify.id == id` — и до запроса списка, и под замком, когда он пришёл; иначе ничего, `debug!` | T61 |
| сверка | `Ambiguous` — только если её запрос списка ушёл не раньше `resolve_after` **этой** правки; иначе ордер не судит (T37) | T62 |
| ответ submit: `note_venue_ack`, `request_settled` | `oid` — только если тот `None` (submit — первый в цепочке, перезапись откатила бы замену); `req` — только если `== New`; `settled_at` — только когда правки в полёте нет | T63, T64 |
| ответ отмены: `cancel_failed` | `req` — только если `== Canceled` | T63 |
| поток: `orderUpdates` | по §5.3 (порядок по oid, P3); b2 при правке в полёте `settled_at` не ставит (сегодня `:403` ставит) | T36 |

Сегодня ответы submit и отмены пишут безусловно (`ordermanager.rs:481, 505-507, 519-520`). Без
правки это безвредно: запрос на cloid один. С правкой поздний ответ submit снимал бы `Replaced` и
открывал ордер сверке посреди правки (T63). После закрытой правки он откатывал бы `oid` на O1:
следующая правка взяла бы `from_oid = O1`, `canceled O2` прошёл бы по (c) как замена — ордер
снят, O3 — сирота (T64). Отказ submit после ack потока — противоречие биржи (приняла и
отвергла), а не порядок; вне MON-4. Как часто поток обгоняет HTTP, покажут сырые метки в
результате пробника (`t_resp_ns` POST, `t_ns` рамок); от этой частоты дизайн не зависит.

### 5.3 `orderUpdates` по cloid X (oid O, статус S); текущий oid ордера — O1

**Ловушка, которую закрывает этот раздел.** Сегодня `canceled` старого oid (cloid X) —
терминал: ордер удаляется из карты и уходит боту `Canceled` (`ordermanager.rs:405-428`);
`open` замены (тот же X) падает в «this process does not track» (`:380`). Итог: ордер стоит на
бирже, ни коннектор, ни бот о нём не знают. Так при **любом** порядке двух записей
(`apply_order_update` переписывает `oid` безусловно, `:405`).

Правила по порядку, срабатывает первое совпавшее; вместе они исчерпывают случаи «O меньше /
равен / больше o1» × «правка в полёте или нет».

| Правило | Условие | Действие | Пин |
|---|---|---|---|
| a | `O1 = Some(o1)`, `O < o1` | устаревшая запись заменённого oid — игнор (debug) | T30, T35, T52 |
| b1 | правка в полёте, `O = from_oid`, S терминальный | `held = update`; боту ничего | T29 |
| b2 | `O1 ∈ {None, Some(O)}` | обычный путь (сторож `update_ts`, статус, `leaves`); `req` = `Replaced`, если правка в полёте, иначе `None` | T36 |
| c | правка в полёте, `O > from_oid` | **замена**: `oid = O`, цена/`qty`/`leaves` из `limitPx`/`origSz`/`sz`, статус из S, `held = None`, `modify = None`, `req = None`, `settled_at = now`; боту — ack (терминальный S — терминал, ордер из карты) | T31, T32 |
| d | правки нет, `O > o1` | замена, которой не ждали (нарушена P1/P2): усыновить, как в c, **и** `error!` + `OrderError` | T53 |

- «Первое определённое свидетельство выигрывает»: замена в потоке (c) закрывает правку раньше
  HTTP-ответа; поздний ответ — no-op (T46), в том числе когда бот уже прислал следующую правку:
  ответ привязан к `id` (§5.2, T60). Поэтому (c) сама ставит `settled_at = now`: поздний ответ
  больше ничего не пишет, и без этого ордер выпал бы из сверки навсегда (T31).
- (a) — сравнением, а не списком: поздняя запись давно заменённого oid во время новой правки не
  принимается за замену. В прежней редакции `retired` на 16 вытеснял старый oid, и тот проходил
  в (c); терминальная запись снимала живой ордер (T52).
- (d) усыновляет только **больший** oid — по P3 это последняя инкарнация того же cloid, поток
  авторитетен (HL-нота §5.5). Но правки не было, значит сломана предпосылка, и потребитель
  должен узнать: `OrderError`, не `warn` (T53).
- b1 держит **любой** терминал: строка, которой биржа гасит старый oid при правке, не
  измерена [Q2] (неизвестная → `Expired` в `map_order_status` — та же ловушка).

**Остаток, принятый осознанно.** Если P1 нарушена (проверяет Q12 до C7) или часы скакнули между
замерами (P2 в рантайме держит сторож, §5.7) **и** терминал `from_oid` обработан раньше `open`
замены, ордер уходит из карты по b2, а замена — «не своя»: видна только в `warn` сверки
«untracked» (`private_stream.rs:385`). Выхода она сама не вызывает; снимет её свип по монете —
при выходе бота по другой причине или остановке коннектора. Надгробие ради этой двойной поломки
не строится (§11.10).

### 5.4 Ответ `/exchange` (`settle_modify(cloid, id, answer)`)

Все строки, кроме первой, — только при `modify.id == id` (§5.2).

| Ответ | Действие | Пин |
|---|---|---|
| не на текущую правку: ордера нет, `modify = None` или `modify.id ≠ id` | ничего не трогать (`oid`, `held`, `phase`, `settled_at`), боту ничего; ошибка при отслеживаемом ордере — `error!` о противоречии (замену показал поток, он авторитетен, §5.5 HL-ноты), прочее — `debug!` | T46, T60 |
| `[Resting{oid: O2}]` / `[Filled{oid: O2}]`, `O2 ≥ from_oid` | `oid = O2` (`=` — правка на месте [Q5]); цена/объём = принятые; `status = New` (у `Filled` дальше статус дают поток и филлы); `exec_* = 0`; `held`: при `O2 > from_oid` отбросить, при `=` применить после ack (решит сторож `update_ts`); `modify = None`; `req = None`; `settled_at = now` → ack | T30, T41 |
| `O2 < from_oid` (в т. ч. oid не прочитан: `unwrap_or(0)` в `parse_status`) | противоречие P3: `error!`, `phase = Ambiguous` → §5.5 | T38 |
| **явный вердикт биржи:** `[Error(r)]` (запись `{"error": …}` в `statuses`) или `Err(ExchangeRejected)` (`{"status":"err"}`; 4xx, кроме 408/425) | `modify = None`; `req = None`; `settled_at = now` → отказ (§2: `request_ts`, `status None`, `exch_timestamp 0`) + `OrderError(r)`; затем, если есть `held`, применить его → терминал боту | T33, T34, T44 |
| **всё прочее:** `[Unrecognised]` (незнакомая форма записи), `[Success]`, `Ok([])`, длина ≠ 1, `Err(ExchangeUnavailable)` (5xx, 408, 425, 1xx/3xx, 200 не-JSON, 200-JSON без `status` или с незнакомым), транспорт | `phase = Ambiguous`; `OrderError` (информационно); **отказа нет**; §5.5 | T42, T43, T66, T67 |

- **Отказ — только явный вердикт биржи.** Сегодня незнакомая форма записи — `ActionOutcome::Error`
  (`parse_status`, `exchange.rs:312, 341`), а 200-JSON без `status` — `ExchangeRejected`
  (`:283-291`), вердикт для `is_venue_verdict` (`mod.rs:181-183`). Правка, исполненная биржей и
  отвеченная в незнакомой форме (смена API, прокси), ушла бы боту отказом с `modify = None` →
  `canceled from_oid` по b2 как терминал, `open` замены — в «does not track»: сирота и двойная
  экспозиция. Меняется (C5): вариант `ActionOutcome::Unrecognised(String)` — для обеих веток
  «незнакомое» в `parse_status`; `error()` отдаёт и его текст, поэтому submit и отмена
  (`private_stream.rs:825, 912`) читают его как сегодня (у submit это тот же класс — незнакомое
  как отказ; вне MON-4); `settle_modify` матчит `Error` явно, не через `error()` (T67).
  Конверт: вердикт — только `"err"`; без `status` или с незнакомым — `ExchangeUnavailable`, как
  200 не-JSON (`:274-281`); не-2xx — вердикт только 4xx, кроме 408/425 (`status_is_ambiguous`,
  `:239-241`, сегодня вердикт и 1xx/3xx) (T66). Правки конверта задевают и submit — в безопасную
  сторону: заявка с таким ответом держится до сверки (§11.7 HL-ноты), а не истекает поверх,
  возможно, стоящего ордера.
- Ack публикуется с `exec_* = 0`: копия коннектора хранит `exec_qty` последнего филла, а ack
  исполнения не несёт (паритет: `modify_acknowledgement_does_not_reapply_the_partial_fill`) (T41).
- `Ok([])` — это и ответ `{"type":"default"}` (`exchange.rs:294-301`): «ничего не отвергнуто»
  для правки **не** подтверждение (T43).

### 5.5 Неопределённость (транспорт, ответ без вердикта)

Задача правки после неоднозначного ответа спит до `resolve_after` (≈ `expires_at + SETTLE`,
SETTLE = 5 с). Если `modify.id` — уже не её `id`, она ничего не делает (`debug!`, список не
запрашивает). Иначе запрашивает список открытых ордеров (`frontendOpenOrders`, таймаут 5 с) и
разрешает правку, **только если под замком `modify.id` — всё ещё её `id`** (T61).
Момент привязан к `expiresAfter` правки, а не к моменту сбоя: сбой бывает и через 50 мс после
отправки, а правка ещё может исполниться (T51). К этому моменту правка исполниться уже не может
[P1, P2], поэтому вывод по списку окончательный — но только о **своей** правке. Таймер по cloid
разрешил бы следующую раньше срока: #1 в `Ambiguous`, поток закрыл #1, бот прислал #2 позже #1
больше чем на SETTLE, #2 тоже `Ambiguous`. Таймер #1 прочёл бы список до `expiresAfter` #2 и
вывел бы «не прошла», а #2 исполнилась бы следом (сирота, «Было» ниже).

**Сверка** разрешает `Ambiguous` той же функцией, но только если её запрос списка ушёл не раньше
`resolve_after` **этой** правки (`queried_at ≥ resolve_after`, T62); иначе ордер не судит (T37).
Сверка идёт сразу на реконнекте и на регистрации бота (`private_stream.rs:258, 352`), а один
сетевой провал роняет и POST, и сокет. Без этого условия реконнект через секунды после сбоя
разрешил бы правку раньше срока.

Чистая функция `resolve_ambiguous_modify(open, cloid, from_oid, request, previous)` (T38);
`previous` — копия коннектора (её цену правка в полёте не меняет; остаток мог обновить b2);
строка X — по cloid или по oid = `from_oid`:

| В списке | Вывод | Действие |
|---|---|---|
| X, у строки не прочитан `limitPx`, `origSz` или `sz` (`None`, «Разбор списка» ниже) | противоречие | `error!`, остаётся `Ambiguous` до сверки |
| X, oid > `from_oid` | прошла | как `Resting{oid}`, цена/объём из списка |
| X, oid = `from_oid`, цену меняли: `limitPx` = запрошенной | прошла на месте [Q5] | ack без смены oid, значения — запрошенные (как §5.4) |
| X, oid = `from_oid`, цену меняли: `limitPx` = прежней | **не прошла — окончательно** | отказ |
| X, oid = `from_oid`, меняли только объём [Q5, S4]: `sz` = `s` | прошла на месте | ack без смены oid |
| X, oid = `from_oid`, меняли только объём: `sz` = остатку копии | **не прошла — окончательно** | отказ |
| X, oid = `from_oid`, прочее (в т. ч. филл в окне правки) | противоречие или неразличимо | `error!`, остаётся `Ambiguous` до сверки |
| X, oid < `from_oid` | противоречие P3 | `error!`, остаётся `Ambiguous` до сверки |
| X нет — список прочитан целиком и несёт cloid (без cloid отсутствие не доказано: как `cloids_are_evidence`, `ordermanager.rs:576`; иначе — как «запрос не удался») | ордера нет | `held` → применить; иначе `Expired` (как `reconcile`) → терминал; плюс отказ |
| запрос не удался (в т. ч. ответ — не список, «Разбор списка») | — | остаётся `Ambiguous`; решает той же функцией первая сверка, чей запрос ушёл после `resolve_after` (на реконнекте или периодическая, `RECONCILE_INTERVAL` 300 с), — это уже за B (§5.6) |

- **Объём на месте — по `sz`, не по `origSz`.** Что HL пишет в `origSz` после правки на месте, не
  измерено [Q5, S4]: «исходный», необновлённый `origSz` при oid = `from_oid` дал бы «не прошла»
  поверх прошедшей правки. `sz` — то, что стоит, поэтому оба окончательных вывода совпадают со
  стоящим (цена, `sz`) при любом пути к нему. Проверка `sz = s` — первой: b2 мог уже переписать
  остаток копии новым `sz`.
- **Разбор списка** (`rest.rs`, C6). Сегодня `OpenOrder` — только `coin`/`oid`/`cloid`
  (`:306-315`), а `parse_open_orders` молча выбрасывает строку с неразборным полем (`?`, `:331`) и
  читает ответ-не-массив как пустой список (`unwrap_or_default`, `:340`). Для §5.5 оба — «X нет» →
  `Expired` и отказ поверх живого ордера; в сверке — `Expired` любого ордера с oid
  (`ordermanager.rs:594`). Меняется: `limit_px`/`orig_sz`/`sz` — `Option<f64>` (строка или число),
  и строка из-за них не выбрасывается; ответ не массив или строка без строкового `coin`/целого
  `oid` — `Err` («не проверено», как `rows_problem` пробника), не `[]` (T68). Существующий пин
  `open_orders_are_read_by_venue_id_with_the_client_id_optional` в частях `partly_broken` → 1
  строка и `null` → 0 пинит прежнее и переписывается: его довод «потеря списка истекает живые
  ордера» обратен коду — ошибка списка не истекает ничего (`private_stream.rs:366-374`; как любая
  ошибка `/info`: сверки нет, на подключении — `ConnectionInterrupted` и реконнект,
  `private_stream.rs:206-231`), а выброшенная строка истекает свой ордер.

- **Было** «список через 5 с после сбоя»: правка, исполненная позже вывода «не прошла» (nonce
  валиден сутки, HL-нота §5.8; edge роняет сокеты), давала сироту O2: `canceled` O1 шёл по b2 как
  терминал, `open` O2 — в «does not track», сверка по oid O2 не видела. Бот котировал поверх.
  SETTLE сужал окно, но не закрывал; `expiresAfter` закрывает построением.
- Противоречие (`held` есть, а список показывает `from_oid` открытым) — `Ambiguous` до сверки,
  `error!`.
- Тот же класс — у **submit** после сбоя транспорта (HL-нота §11.7: ордер держится, сверка
  истекает его по `cloids_are_evidence`; исполнись `order` позже — сирота). Лечится тем же
  `expiresAfter` на `order` — вне MON-4, отдельный пункт.

### 5.6 Граница B — граница штатного пути

Штатный путь: локальный отказ/ack — сразу; ответ биржи — ≤ `EXCHANGE_TIMEOUT` (10 с);
неопределённость — `expiresAfter` (10 с от подписи) + SETTLE 5 с + запрос списка 5 с =
**B = 20 с от подписи** (не от отправки ботом: до подписи — IPC, приём, спавн задачи; после
разрешения — публикация). Не удался и запрос списка или список не различил исход (§5.5) — это уже
**сбой**: ответ ждёт сверку (≤ 300 с, а при повторных неудачах — дольше). Гейт потребителя (B + 5 с
от `local_timestamp`, §6) в этом случае выводит бота — fail closed, так задумано. Умолчание
(bybit/binance/lighter) — сразу. Пины: T51 (до `expires_at + SETTLE` список не запрашивается,
после — ровно один раз), T19 (бот ждёт параметр MON-11, а не 60 с).

### 5.7 Локальные отказы и локальный ack (без запроса к бирже, бюджет 0)

Отказ: `(symbol, order_id)` неизвестен; торговля не настроена (нет ключа, T45); asset index
неизвестен; ордер не активен; oid ещё неизвестен (submit без ack и без записи в потоке); в
полёте любой запрос (`modify` или `req != None`, T26); ошибка нормализации (T27); **часы** — замера
ещё нет или последний d вне ±2 с (T69). Задача правки, которую поток уже закрыл, а HTTP ещё не
ответил, — не «в полёте»: её ответ ничего не решает (§5.4, T60), и следующая правка идёт сразу.

- **Сторож часов** — P2 в рантайме (§1.1). d = наши часы (`SystemTime`, как у nonce и
  `expiresAfter`) − заголовок `Date`; пишется с каждого ответа `ExchangeClient::post` и
  `rest::info` в общий `Arc` рядом с `NonceSource`, последний замер побеждает. `Date` — с
  точностью до секунды и проставлен до транзита, поэтому d ≥ сдвига: |d| ≤ 2 с ⇒ спешат не больше
  2 с (P2 требует < 4 с); здоровый хост даёт d ∈ [0, 1 с + транзит). Отказ, а не сдвиг
  `resolve_after` на d: сдвиг растянул бы B, а гейт потребителя — константа (§6); отказ же —
  штатный трафик (Р4).
- **Отмена, пока правка в полёте** (Р3), — тоже локальный отказ. Бот при `Replaced` её не шлёт
  (`cancellable()`), но после копии §3.3 пришлёт. Сегодня `cancel_order` безусловно зовёт
  `mark_requested(Canceled)` (`private_stream.rs:905`) и перезаписал бы `Replaced`, а
  `cancel_failed` снял бы `req` посреди правки. Теперь `OrderManager::cancel_order` при
  `modify.is_some()` — отказ: ни запроса, ни `mark_requested`, правка не тронута; боту — отказ
  формы §2 (эхо метки отмены; ветка §3.2: `Canceled → None`) и `OrderError` (T70). Не копия с
  `Replaced`: отказ правки несёт свою метку, бот после отмены его не применил бы и держал бы
  `Replaced` до гейта. Не одна `OrderError`: бот остался бы в `req = Canceled`, а гейт (§6) смотрит
  только `Replaced`.

**Ack без запроса:** после нормализации цена и объём равны текущим — экономит запрос и место
в очереди; паритет с in-place веткой `ack_modify` (T28).

### 5.8 Филлы, свип, сверка, отмена после правки

- `userFills` — по cloid, без изменений. В полёте копия уходит с `req = Replaced` (T36). Поздний
  филл старого oid после ack применяется по cloid; позиция — из `startPosition` филла.
- Свип: `cancel_confirmed(oid)` (`ordermanager.rs:530`) матчит только по oid; добавить cloid из
  списка биржи — на случай устаревшего oid (T39).
- **Сверка — по cloid тоже** (T54): у отслеживаемого X с oid o1 биржа листит X с oid > o1 → не
  истекать (сегодня `ordermanager.rs:594` матчит только по oid и опубликовал бы `Expired` поверх
  живого ордера), а усыновить по правилу d: `error!` + `OrderError`. Ордер с правкой в полёте не
  судит (T37); `Ambiguous` разрешает §5.5, сверкой — только запросом, ушедшим не раньше
  `resolve_after` этой правки (T62). `tracks()` (cloid или oid) — без изменений.
- Отмена после правки — `cancelByCloid`, снимает замену [F6]. Опровергнет [Q9] — отмена
  модифицированных ордеров идёт `cancel` по oid (`CancelAction` уже есть для свипа).
- **Гонка свипа с правкой в полёте — два пути, оба открыты:**
  1. свип остановки (`SweepReason::ConnectorStopping`, `main.rs:911`): приём запросов
     остановлен, а спавненная задача `batchModify` ещё в полёте;
  2. свип по смерти бота (`SweepReason::BotDied`, `main.rs:244-278`): бот умер сразу после
     `modify`; свип идёт через `bot_liveness.timeout_ms` (10 с) после последнего heartbeat, а
     правка может исполниться до `expiresAfter` = подпись + 10 с — окно ≈ интервал heartbeat +
     лаг индексации.

  Механизм один: `Sweeper::cancel_all` (`private_stream.rs:607`) снимает список до появления
  замены, отменяет O1 («never placed…»), O2 остаётся сиротой. Тот же класс — submit в полёте.
  **Кандидат на лечение** (не в MON-4): свип символа после первого прохода ждёт
  `max(expires_at) + SETTLE` по ордерным задачам этого символа в полёте и повторяет список.
  С `expiresAfter` второй проход окончателен для правок; для submit нужен `expiresAfter` на
  `order` (§5.5).

### 5.9 Сверх капа

Правка — не отмена: в режиме «одно действие в 10 с» [README econ] проходит как ордер, отмены —
сразу. Отказ «Too many cumulative requests» → ордер стоит по старой цене, `req = None`. Для
мейкера это приколотая котировка; выход — отмена. Политика (myhft, модуль бюджета), не
библиотека. Просроченная правка (P2) выглядит так же; что она списывает — [Q12].

## 6. Старый коннектор + новый бот, MON-11

- По умолчанию (`native_modify = false`) новый бот правку не шлёт — пара «новый бот + старый
  коннектор» безопасна без условий (T58).
- С `native_modify(true)` и старым коннектором `run_receive_task` отвечает
  `error!("An invalid request…")`, ответа нет никогда:
  - `wait = false`: ордер в `Replaced`; `cancel()`/`modify()` → `InvalidOrderStatus`. Котировка
    приколота до (а) любого `Order`-события по ордеру от старого коннектора (его копия несёт
    `req = None`, `update()` снимает флаг) или (б) выхода процесса → свип по живости (10 с) или
    при остановке.
  - `wait = true`: блок на весь таймаут — сегодня зашитые 60 с (`bot.rs:878`, `:1078`). Поэтому
    **MON-11 — пререквизит**: коммит с `LiveBot::modify` не едет без параметра; T19 без него не
    пишется.
- Обнаружимость: контракт «новый коннектор отвечает за ≤ B от подписи» (§5.6: HL 20 с, умолчание
  ~0). Гейт потребителя: `req == Replaced && now − local_timestamp > B + 5 с` (HL — 25 с) ⇒
  коннектор старый или сломан ⇒ fail closed (политика потребителя, §1.1: выход → свип). Запас —
  потому что `local_timestamp` — отправка ботом, а не подпись: IPC, приём, спавн задачи и
  публикация ответа ложатся сверх B, и гейт ровно на B срабатывал бы на здоровом худшем пути.
  Гейт нужен и при новом коннекторе: за B — сбой (§5.6). Библиотека флаг сама не снимает (§11.6).
  Пин гейта — в myhft, вместе с ним: ответ на B от подписи, доставленный позже B от отправки, бота
  не роняет; мутация — порог B.
- **Отказ правки — штатный трафик** (§14 Р4): на HL — например, ALO-правка через тач [Q13], у
  бэкенда без правки — каждая (T9). `OrderError` при нём не фатален (myhft уже так, пин
  `handle_live_error_order_error_is_non_fatal`); стратегия откатывается на cancel+new. Поэтому
  `native_modify(true)` — только боту, **все** коннекторы которого правку реализуют (сегодня —
  HL ≥ C7). ≥ C3 — условие совместимости (котировку не приколет), а не полезности: бот с HL и
  bybit получал бы на bybit отказ на каждую правку — лишний круг до коннектора и `OrderError` в
  журнал перед каждым cancel+new.
- Выкладка: коннектор ≥ C3 везде → бот ≥ C4 → `native_modify(true)` в myhft — только ботам, у
  которых все коннекторы ≥ C7 (HL). Пин myhft — только на опубликованный коммит (§5 Git
  `AGENTS.md`).

  `user or api wallet`, `insufficient margin`, `invalid nonce`); широкие «nonce», «rate limit»,
  «too many» — не аборт, а пометка шага `text_flags` (`?? mentions …` в строке шага и сводке):

- **Выход.** Любой сигнал, который по умолчанию завершил бы процесс и приходит снаружи
  (`Stopper.SIGNALS`: INT, TERM, HUP, QUIT, USR1, USR2, ALRM, VTALRM, PROF, IO, PWR, XCPU, XFSZ), →
  план останавливается после текущего запроса; очистка — при любом исходе; сигнал во время
  очистки игнорируется (она ограничена 120 с и кончается сама). Мимо очистки уходят только
  SIGKILL (`kill -9`, OOM-killer), смерть машины, сигналы аварии самого интерпретатора (SIGSEGV,
  SIGBUS, SIGILL, SIGFPE, SIGABRT, SIGTRAP, SIGSYS — обработчик на Python вернул бы управление в
  упавшую инструкцию) и сигналы без имени в модуле `signal` (SIGSTKFLT, real-time — их шлют только
  руками); потом `--sweep-only`. Ctrl-Z (и SIGTTIN/SIGTTOU у фонового процесса) не завершает, а
  замораживает процесс — вместе с его ордерами. Очистка повторяет `/info` (до 6 раз);
  `{}`, `{"error": …}`, `false`, `null` вместо списка — «не проверено», а не «чисто»; «чисто» —
  два пустых списка подряд с паузой. Затем `userFills` и позиция по монете против старта.
  Свёртка (очистка, сверка, запись результатов, печать) — каждый шаг в своём `try`: сбой одного
  не отменяет следующих (`wind_down_failures`); результаты пишутся всегда и до печати. Печать не
  бросает: если терминал пропал (обрыв SSH, закрытое окно — SIGHUP, затем EIO на каждый write),
  упавший поток вывода уходит в `<UTC>_hl_modify_probe_console.log` рядом с результатами, здоровый
  (stderr в файл) остаётся где был; ошибка кодировки — не обрыв: stdout экранирует символ
  (`backslashreplace`). Коды: 0 — чисто; 2 — аборт/филл/позиция изменилась/сверка
  или запись результатов не удались; 3 — отказ, ничего не отправлено; **4 — ордера пробника,
  возможно, остались** (громко; `--sweep-only` — или руками, если ответ биржи приписал прогону
  строку без cloid).
- **Прочее.** Один прогон за раз (`flock` в каталоге состояния). Ключ — только из `--config`, не
  печатается. Работающий HL-коннектор с тем же файлом ключей или тем же API-кошельком — отказ;
  коннектор, чей файл ключей не определить (чужой uid, относительный путь), или на том же счёте —
  предупреждение.

## 11. Отвергнуто

1. **Новый `LiveRequest::Modify`** — смена провода и парный апгрейд ради того, что уже выражает
   `Replaced`.
2. **Одиночный `modify`** — нет oid в ack [F2], форма отказа неизвестна; цена та же [F1].
3. **Оптимистичный вид в полёте (как бэктест)** — на отказе нужно вернуть старые цену/объём;
   коннектор по умолчанию их не знает (в запросе только новые) → побочная таблица в боте, а
   ошибка возврата = невидимая экспозиция. Консервативному виду возвращать нечего.
4. **Отмена поверх правки в полёте** — единственный выход из приколотой котировки без выхода
   процесса. Цена: расхождение с бэктестом или правка апстримного `Local::cancel`, плюс
   параллельные cancel/modify в коннекторе. Отложено (в v1 — локальный отказ, §14 Р3, T70):
   граница B (§5.6) и свип покрывают; пересмотреть, если неопределённость окажется частой (§14.1).
5. **`native_modify` включён по умолчанию** — новый бот со старым коннектором приколол бы
   котировку до гейта потребителя; §1.1 `AGENTS.md` требует запрещающих умолчаний (прецедент —
   `heartbeat_interval(None)` как аварийный выход). Принят opt-in (§0.3).
6. **Бот сам снимает `Replaced` по таймауту** — врёт, когда правка на бирже прошла.
7. **Новый cloid на каждую правку** — ключ карты коннектора меняется на каждой правке, филлы и
   отмены надо переадресовывать; cloid сохраняется [F3, F6] — ключ стабилен.
8. **Склейка n запросов бота в один `batchModify`** — адресный бюджет тот же (n за n) [F1];
   выигрыш только IP-вес и RTT, а трейт по-ордерный → буфер с таймером. v2, когда IP-вес
   ордерных действий станет заметной долей 1200/мин.
9. **`Bot::modify_many`** — новый обязательный метод трейта (§2: обе реализации и все внешние
   импл), ради выигрыша из п. 8, которого в бюджете нет.
10. **Надгробие после «не прошла»** (N минут держать терминал `from_oid`, усыновлять `open` по X с
    новым oid) — `expiresAfter` закрывает позднее исполнение построением; надгробие покрыло бы
    только двойную поломку (P1/P2 нарушены **и** терминал раньше замены) ценой ещё одной фазы
    автомата и таймера. Детектор (правило d, T53; сверка по cloid, T54) и свип по монете —
    достаточно. Пересмотреть, если Q12 опровергнет P1.
11. **Вывод по списку через SETTLE после сбоя, без `expiresAfter`** (прежний §5.5) — правка,
    исполненная после вывода «не прошла», давала сироту и двойную экспозицию; SETTLE сужал окно,
    не закрывал.
12. **`retired` на 16 oid** — вытеснение пропускало старый oid в правило c; сравнение по P3 проще
    и без потолка.
13. **Ответ и таймер правки — по cloid** (прежние §5.4–5.5): cloid сохраняется и запрос не
    называет. Поздний `Resting{O2}` #1 закрывал #2 строкой «на месте» до её исполнения, таймер #1
    разрешал #2 раньше её `expiresAfter`; итог — сирота без единого сбоя (§5.2). У submit cloid
    уникален, и корреляции по cloid хватало, пока по тому же cloid не пошла правка (T63, T64).
14. **`request_ts` как идентичность запроса** — он от бота (`Utc::now()` чужого процесса) и
    уникален лишь по допущению о его часах: шаг назад, грубое разрешение, подставные часы в
    тесте. Счётчик коннектора уникален построением; цена — счётчик в `OrderManager` и `id` в
    `PendingModify`.
15. **Держать правку «в полёте» до HTTP-ответа, даже когда поток показал замену** — тогда `id` не
    нужен ответу, но следующая правка на штатном (частом) пути — поток раньше HTTP — получает
    ложный локальный отказ с `OrderError`. Это не выход (у myhft `OrderError` не фатален:
    `handle_live_error` → `Ok(())`, `src/lib.rs:252, 296-300`), а цена каждой такой перекотировки:
    круг до коннектора впустую, `error!` в журнал, откат на cancel+new — 2 запроса вместо 1. В §3.3
    (Р2) тот же отказ принят, потому что там он редок. Вариант «ack только по HTTP» добавляет RTT
    к каждой перекотировке, а таймеру идентичность нужна всё равно.
