# Design: live-коннектор Lighter (zkLighter)

Статус: **Draft, адверсариальное ревью не проходил** (задача заведена). Автор черновика — сессия 2026-07-30.
Связано: `collector/src/lighter/` (работающий read-only бэкенд — источник всех «замерено» ниже),
`docs/design-hyperliquid-connector.md` (паттерны, которые здесь переиспользуются),
`docs/research-symbol-selection.md` (зачем вообще: нулевые комиссии против комиссионного пола 3.0 б.п.).

## 1. Зачем

Пассивная сетка на HL платит 3.0 б.п. за круг — это главный член её экономики и главный фильтр
отбора монет. **На Lighter стандартный аккаунт торгует с нулевой комиссией** (verify: актуальность
и условия — открытый вопрос №1). Если стаканы Lighter дают вменяемую глубину и незанятый тач —
а это ровно то, что наша запись 15 монет уже копит, — сетка там экономически свободнее на весь
комиссионный пол. Решение о Phase 2+ принимается по этой записи, не раньше.

## 2. Что уже известно (замерено коллектором, mainnet 2026-07-28)

- Эндпоинты: WS `wss://mainnet.zklighter.elliot.ai/stream`, REST `https://mainnet.zklighter.elliot.ai`;
  тестнет — `testnet.zklighter.elliot.ai`. Токио → mainnet ~3 мс.
- Каталог: `GET /api/v1/orderBooks` — 227 стаканов, адресация по `market_id`; символ → id
  резолвится динамически (коллектор так и делает). Там же пер-маркет декимали цены/размера.
- **Стакан инкрементальный**: канал `order_book` шлёт снапшот на подписку, затем дельты.
  Разрыв последовательности чинится только `unsubscribe → subscribe` (повторная подписка без
  отписки → ошибка 30003 «Already Subscribed»); раунд-трип репейра замерен: 522 мс.
- Клиентский рейт-лимит WS-сообщений: ~200/мин — подписки и репейры надо бюджетировать.
- Геоблок существует; проверка достижимости — обязательная часть старта (у коллектора есть probe).

## 3. Решения (с отвергнутыми альтернативами)

### 3.1 Depth: дельты — напрямую в вид 1, зеркало — только для ресинка

Дельты `order_book` мапятся в `LOCAL_*_DEPTH_EVENT` (вид 1) один в один — в отличие от HL здесь
**не нужно** синтезировать дифф на каждый кадр. Но `LiveBot` игнорирует снапшоты (AGENTS.md §4.1),
а репейр после разрыва начинается со снапшота. Поэтому коннектор держит лёгкое зеркало книги и на
ресинке **диффует старое состояние против нового снапшота, эмитя только вид 1** (снятые уровни —
нулевым объёмом, удаления раньше вставок — переиспользовать механику `DepthMirror` HL-бэкенда,
она ровно про это). Отвергнуто: слать `DEPTH_SNAPSHOT_EVENT` (бот его выбросит — §4.1, вечно
пустой стакан); держать полное зеркало на каждый кадр (лишняя работа: дельты и так самодостаточны).

### 3.2 Подпись транзакций: spike решает, Rust-порт против sidecar-подписанта

zkLighter подписывает транзакции (CreateOrder/CancelOrder/...) собственной схемой; официальные
SDK (lighter-python/lighter-go) несут нативный подписант. Два пути: (а) портировать схему в Rust
(риск: криптографию переписывать страшно, нужны golden-векторы из SDK на каждый тип транзакции —
как мы делали с EIP-712 у HL); (б) sidecar-процесс с SDK-подписантом (риск: ещё один процесс в
money path, латентность IPC на каждый ордер). **Решение отложено до Phase 0 spike**: если схема
окажется композицией известных примитивов с доступными тест-векторами — Rust-порт; иначе sidecar
как временная ступень. Отвергнуто сразу: подписывать «по мотивам документации» без golden-векторов.

### 3.3 Nonce: единственный владелец — задача ордерного пути

По изысканиям fundarb, tx-nonce у Lighter цепочечный (begin_nonce привязан к предыдущему;
параллельные отправки с зазором ломают цепочку) — **verify в Phase 0**. Дизайн под это: один
tokio-таск владеет nonce и очередью исходящих транзакций (single-writer, как OrderManager у HL);
все submit/cancel идут через него. Отвергнуто: nonce за мьютексом у произвольных вызывающих —
гонка на ровном месте.

### 3.4 Приватное состояние и реконсиляция

Приватные WS-каналы аккаунта (позиции/ордера/филлы) — форма подписки и auth **не изучены**
(коллектор публичный). Требования те же, что доказаны у HL: replay-устойчивость (dedup),
позиция от venue как источник истины, cancel-all на регистрацию символа/рестарт — политика
«чистый лист» из snapshot-marker-ноты переносится как есть.

### 3.5 Адресация и конфиг

Символы в конфиге — строки биржи (как везде); `market_id` резолвится на регистрацию из каталога
с фатальным отказом на неизвестный символ (паттерн валидации коллектора). Декимали цены/размера —
из каталога же, квантизация котировок на стороне коннектора (как HL-нормализация).

## 4. Ловушки, известные заранее

- **Экономическая предпосылка может протухнуть**: нулевые комиссии — это сегодняшняя политика
  площадки, не закон природы. Пересматривать при каждом изменении их fee schedule; сетка,
  прибыльная при нуле, при 1 б.п. за сторону может умереть.
- **Стаканы тоньше HL** (наша же запись: lighter-зеркала легче HL-фидов) — размер и шаг сетки
  надо будет считать от их глубины, не переносить HL-параметры.
- Бюджет 200 msgs/мин: N символов × (подписка + редкие репейры) — влезает с запасом, но storm
  репейров при нестабильной сети может упереться; репейры троттлить.
- Wire-протокол наш: `MAX_PAYLOAD_SIZE = 512` — длинные символы/ид Lighter проверить на влезание.
- Все «замерено» выше — mainnet; тестнет может отличаться каденциями и каталогом.

## 5. Фазовка

- **Phase 0 — spike (задача #28)**: изучить SDK-подписант, получить golden-векторы, вручную
  провести один ордер на тестнете end-to-end; verify nonce-модель и приватные каналы. Выход —
  обновление §3.2/§3.3/§3.4 этой ноты с «замерено» вместо «verify».
- **Phase 1 — маркет-дата бэкенд** в `connector/`: order_book→вид 1, trades, ресинк-зеркало,
  переподписка по образцу §4.2 (SharedSymbolSet + SubscriptionTracker — уже общие в utils.rs).
  Тесты на фикстурах из **реальных** записей коллектора (они уже в testdata-практике).
- **Phase 2 — ордерный путь**: подписант, nonce-владелец, submit/cancel, приватное состояние,
  реконсиляция, тестнет-сетка end-to-end (критерий тот же, что был у HL: живой LiveBot, реальные
  филлы, позиция сходится с venue).
- **Phase 3 — mainnet на минималках**, параллельно с HL-лайвом, решение — по записи стаканов
  Lighter и вердикту переранжирования.

## 6. Открытые вопросы

1. Актуальные комиссии и их условия (стандарт/премиум аккаунты, объёмные пороги).
2. Схема подписи: примитивы, доступность тест-векторов, стоимость Rust-порта.
3. Nonce-модель под нагрузкой: сериализация против окна параллельных tx.
4. Приватные каналы: auth, форма подписки, replay-семантика, наличие снапшота состояния.
5. Post-only/ALO-эквивалент и TIF-набор; маппинг client order id в наш `u64`.
6. Rate-limit ордерного пути (отдельный от WS-сообщений?) и его коды ошибок.
7. Минимальные размеры ордеров по маркетам — влезает ли «измерительный» размер сетки.
8. Тестнет: есть ли кран, совпадает ли каталог с mainnet.
